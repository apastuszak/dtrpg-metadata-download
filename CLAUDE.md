# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository. It states the current rules and architecture; see [docs/HISTORY.md](docs/HISTORY.md) for the verification stories and bug post-mortems behind the non-obvious ones — read that when you want the "why," or before touching an area that's bitten this project before.

## What this is

A pipeline that matches local RPG PDF filenames against DriveThruRPG metadata (purchased library, then public catalog, then manual overrides) and writes the result one of three ways, chosen by `--metadata` (`pdf_writer.METADATA_MODES`: `off`/`calibre`/`grimmory`/`bookorbit`, default `grimmory`): Calibre-format XMP embedded in the PDF, optionally plus a Grimmory `.metadata.json` sidecar, or instead only a BookOrbit `.opf` sidecar (see `sidecar_writer.py`). There is no database and no long-running service — it's a CLI run manually against a folder of PDFs. Current policy is Calibre-format embedded metadata (universal, not reader-specific) plus per-reader sidecars for apps with their own sidecar convention — Kavita, then BookOrbit-only embedded XMP, were both tried and superseded (`kavita_client.py` was deleted as dead code once Kavita was dropped).

## Setup and running

No `pyproject.toml`/`setup.py` — this is a flat script directory, not a packaged/installable project. `dtrpg-metadata-download.py` carries its own dependency list as [PEP 723](https://peps.python.org/pep-0723/) inline script metadata (the `# /// script` block at the top) and is executable directly — no manual venv:

```bash
export DTRPG_API_KEY=...   # Application Key from the DriveThruRPG account page, NOT the account password
./dtrpg-metadata-download.py <subcommand>
```

`uv` resolves and caches the dependencies (pikepdf/rapidfuzz/PyYAML/requests/lxml/textual/pymupdf/pillow/PyQt6) transparently on first run via the shebang (`#!/usr/bin/env -S uv run --script`); every run after that is instant, no `.venv` involved. `requirements.txt` + a classic `python3 -m venv .venv && ./.venv/bin/pip install -r requirements.txt` still works too, for anyone without `uv` — keep both in sync if dependencies change. Subcommands:

- `tag PDF_PATH` / `tag --root DIR [--metadata MODE] [--rename]` — with `--metadata off`, `TagApp`/`TagFlowController._process_one()` skip matching entirely (no client is built, no batch-series/candidate/confirm screens): only the file options run, and `--rename` reads the metadata already on disk (`do_rename(path)` with no title → `renamer.read_title_and_series()`). Otherwise a full-screen Textual TUI (`tag_tui.py`), no review.csv, both for a single file and for --root's per-file loop (one code path, not two). This is the primary/actively-used path. See "Interactive UI (`tag_tui.py`)" below for the screen-by-screen design; the CLI surface here (`tag_parser`'s flags, guard clauses) is unchanged from before the TUI rewrite — `cmd_tag()` is a thin dispatch that constructs and runs a `TagApp`.
- `scan --root DIR [--refresh-library] [--apply-review]` → `write-pdfs --root DIR [--metadata MODE]` — batch path gated by `data/review.csv`: `scan` matches everything and writes rows to the CSV (never auto-writes PDFs), you hand-edit `status` to `approved`, then `write-pdfs` applies only approved/auto-accepted rows. `all` runs both in sequence.
- `review-status` — prints CSV status counts.
- `rename PDF_PATH` / `rename --root DIR [--dry-run]` — renames each already-tagged PDF (plus its `.bak`/`.opf`/`.metadata.json`/`_link_report.csv`) to `<series> - <title>.pdf`, reading title/series back from the first of the `.metadata.json` sidecar, the `.opf` sidecar, or the embedded Calibre XMP that has a title (`renamer.read_title_and_series()` — the XMP series is read from the raw packet with lxml, since pikepdf's public API can't read that structured property back reliably, the same limitation the writer has). `tag --rename` passes the confirmed title/series straight to `plan_rename()` instead, so it works under `--metadata off`. Untagged files and files already named correctly are skipped; a computed name that collides with an existing file is left alone and reported as failed, never overwritten (unless the "collision" is the same file under a different case on a case-insensitive filesystem — see `renamer.py`'s `samefile()` check). Renames a file's whole companion group atomically-ish — a mid-group OS failure rolls back whatever already succeeded rather than leaving `.pdf`/sidecars split across old and new names.
- `--metadata MODE` (on `tag`/`write-pdfs`/`all`; the GUI's "Metadata tagging" dropdown, `_add_metadata_picker()`) — `off` writes no metadata (other steps still run; a file nothing changes isn't even backed up), `calibre` embedded XMP only, `grimmory` (default — what this tool always wrote before the choice existed) embedded XMP + `.metadata.json`, `bookorbit` wipes all PDF metadata and writes only the `.opf` (see the BookOrbit sidecar section below). Each mode but `off` deletes a stale sidecar it doesn't write. `--bookorbit-mode` is a hidden `store_const` alias for `--metadata bookorbit` in the same mutually exclusive group (the same pattern as the `--hyperlink-*` aliases).
- `--convert-images` (on `tag`/`write-pdfs`/`all`) — converts CMYK/grayscale/JPEG2000 images in the PDF to RGB JPEG via `image_converter.py`, before metadata is written. See "Image conversion (`image_converter.py`)" below.
- `--page-labels` (on `tag`/`write-pdfs`/`all`) — sets `/PageLabels` (Cover / i, ii, … / printed page numbers) automatically from page headers/footers. See "Page labels (`page_labels.py`)" below.
- `--back-cover-to-page-2` / `--back-cover-to-end` (on `tag`/`write-pdfs`/`all`, mutually exclusive) — moves the back cover right after the front cover, or to the end. See "Back cover moves (`back_cover.py`)" below.
- `page-labels PDF_PATH` / `page-labels --root DIR [--dry-run]` — the same labeling standalone, for already-tagged books (one-time `.bak` first, nothing else in the file changed). Modeled on `rename`. Neither has a GUI tab: the Tag tab with Metadata tagging off replaced both, and its GUI-only **Dry run** (`TagFlowController.dry_run`) previews them via `gui_app._label_one()`/`_rename_one()` (no matching, nothing written, every other option ignored) — `test_controller_metadata_off_dry_run_then_write` guards it.
- `gui` — a desktop GUI (PyQt6, `gui_app.py`/`gui_tag_flow.py`) covering every subcommand above in one window, including an editable table for `review.csv` instead of hand-editing it in a spreadsheet. See "Desktop GUI" below for the architecture. PyQt6 is a normal dependency (installed automatically via `uv run --script`, same as every other dependency here) — no system-level prerequisite.
- `preferences` — view/edit a saved API key and DriveThruRPG account name (`preferences_tui.py`; also a Preferences tab in the GUI). See "Preferences" below.

`config.yaml` supplies defaults (root, thresholds, cache paths); CLI flags override it. Copy/edit it per-machine — it's meant to stay free of secrets. The API key comes from `DTRPG_API_KEY` if set, or otherwise from `data/preferences.yaml` (gitignored, owner-only file permissions) — see "Preferences (`preferences.py`/`preferences_tui.py`)" below for the security trade-off this deliberately takes on, and why the environment variable still wins when both are present. Every relative path in `config.yaml` (`data_dir`/`review_csv`/`manual_overrides`/`preferences`) resolves against `config.yaml`'s own location, not the current working directory — `root` is the one deliberate exception, since it behaves like a CLI argument.

**Match precedence** (checked in this order, in both `tag` and `scan`, via `matcher.match_file()`/`_tag_one()`): `data/manual_overrides.yaml` (full hand-typed metadata, for titles not on DriveThruRPG at all) → `<root>/dtrpg_urls.csv` (just `filename,drivethrurpg_url` — lives alongside the PDFs it describes, not in `data/`; full metadata is fetched live via `DtrpgClient.get_product()`; auto-approved with no confirmation prompt even in `tag`, falls back to search if the fetch fails) → purchased library → public catalog.

**`load_manual_overrides()`** reads each field with `meta.get(key) or default`, never `.get(key, default)` — a present-but-blank field (e.g. `source:` with nothing after it) parses to an explicit YAML `null`, which `.get(key, default)` returns as-is instead of falling back (see HISTORY.md for the crash this used to cause). A non-dict entry (a bare `filename.pdf:` line with nothing indented under it) is skipped with a warning rather than crashing the whole file; an invalid `source:` value falls back to `manual` with a warning. An entry can also carry an explicit `product_id:`, or one is derived from `product_url` via `extract_product_id()` if not given — without one, an overridden book's `dc:identifier` is empty.

## No test suite (with two scoped exceptions)

There's no pytest/unittest scaffolding and no lint config in this repo. Verification during development has been done with ad hoc inline Python scripts: build a throwaway PDF with `pikepdf.new()`, run it through `matcher`/`pdf_writer` with a `unittest.mock.MagicMock()` standing in for `DtrpgClient` (to avoid live API calls), then reopen the PDF and assert on what was actually written — not just that the code ran without raising. When the real API's response shape needs checking, `data/debug/*.txt` dumps (raw response bodies, written automatically on any parse failure — see below) are the source of truth; prefer replaying a real captured dump over guessing at shape from third-party code.

**`tests/test_tag_tui.py` and `tests/test_gui_app.py` are the two committed exceptions**, added deliberately when `tag` was rewritten as a Textual TUI and when the desktop GUI was built. Both cover the request/response wiring between a background worker (a Textual worker / a `QThread`) and its UI-thread dialogs — a wrong widget id or a dropped `await`/signal silently breaks a whole interactive path in a way that's easy to miss reading the code and easy to never notice by hand (you'd have to click through every path, every time, to catch a regression). Both are plain runnable scripts (`./tests/test_tag_tui.py`, `./tests/test_gui_app.py`), no pytest/framework beyond `Textual`'s own `App.run_test()`/`Pilot` and `PyQt6.QtTest.QTest` respectively — matching this project's "runnable script, not a framework" convention even in the one place it has committed tests. Both have already caught real bugs, not just theoretical ones — see HISTORY.md's "Testing" section for specifics, and its "GUI: Tkinter → PyQt6 migration" section for why `test_gui_app.py` replaced an earlier Tkinter-based suite.

**Reading back with `pikepdf.open(...).open_metadata().get(...)` is not sufficient on its own for Calibre-specific structured fields.** A malformed `calibre:series` write can round-trip through pikepdf perfectly (pikepdf will happily read back whatever it wrote) while being completely invisible to the real target app, which parses the raw XMP independently and can have structural requirements pikepdf's generic reader doesn't enforce. For anything Calibre-, BookOrbit-, or Grimmory-specific, verify against the real thing: `ebook-meta`/`ebook-meta --to-opf` (Calibre is installed locally) on a PDF this project actually wrote, or — for BookOrbit/Grimmory — fetch that app's real open-source parser and run it directly via `npx tsx` against a generated file (`pdf-lib`/`fast-xml-parser` are the only npm deps needed). A field that "looks right" only by pikepdf's own reading of its own write has not actually been verified — see HISTORY.md's "Calibre series bug" for exactly how this went undetected for most of this project's history.

## Architecture

**Module chain:** `dtrpg_client.py` (network + caching) → `matcher.py` (filename→query, fuzzy scoring, decides `ReviewRow`/candidate list) → `review.py` (CSV I/O, only used by the batch path) → `pdf_writer.py` (writes XMP via pikepdf, then calls `sidecar_writer.py` for the `.opf`/`.metadata.json` files) → `dtrpg-metadata-download.py` (CLI, wires it all together). `provenance.py` holds the two shared types (`ProductMetadata`, and the `Source`/`Status` enums) that every other module imports. `page_labels.py` (detection/planning/`/PageLabels` writing), `back_cover.py` (the cover move) and `rpg_hyperlink.py` (→ `hyperlink_engine.py` + `hyperlink_checks.py` + `hyperlink_rules/`) are called from `pdf_writer.py`; the first two use `page_render.py` to find back covers. `renamer.py` is a separate, independent leaf off the CLI — it runs *after* tagging, reading back already-written metadata (a sidecar, or the embedded XMP) to rename files, rather than participating in the match/write chain itself. `tag_tui.py` is `tag`'s presentation layer — it calls into `matcher`/`pdf_writer`/`renamer` exactly the way `dtrpg-metadata-download.py` itself does for every other subcommand, and none of those modules know or care that `tag` is a TUI rather than `print()`/`input()`.

**Interactive UI (`tag_tui.py`):** a Textual app, added specifically so manual metadata entry could have a real multi-line text area for Description (`input()` can't do that) — see the module's own docstring for the full screen-by-screen mapping from the old `_tag_one()`/`_manual_entry_flow()`/`_prompt_manual_metadata()` functions (all deleted; only `_rename_one` stayed in `dtrpg-metadata-download.py`, still needed by `cmd_rename`). One `TagApp` instance handles a whole run — single file or `--root` batch alike, one code path instead of two. Orchestration is a single linear coroutine (`TagApp._run_flow`, run as a Textual worker) that `await self.push_screen_wait(...)`s through each file in turn, not a `Message`-passing state machine — a direct async translation of the old procedural `cmd_tag()`/`_tag_one()` control flow. (`push_screen_wait()` — push a screen, `await` its `dismiss()` result — only works from inside a worker; that's why `_run_flow` is `@work`-decorated rather than called directly from `on_mount`.) Every blocking call (`DtrpgClient.search_library`/`get_product`/`enrich`, `write_metadata()`, `plan_rename()`/`apply_rename()` — all synchronous pikepdf/requests I/O) goes through `TagApp._call()`, a thin `asyncio.to_thread()` wrapper, so the UI doesn't freeze while one is in flight.

`ConfirmScreen` shows every field about to be written as an editable form (title, publisher, series, series index, description, tags, ISBN, product URL), pre-filled from the matched/overridden `ProductMetadata`. `TagApp.action_confirm()`'s edited values are rebuilt into a `ProductMetadata` by `apply_edits()` (a `dataclasses.replace()` over the original match, so `source`/`authors`/`product_id` survive untouched even if title/series/etc. are hand-edited — `product_id` in particular has to stay whatever was actually fetched, or `dc:identifier` and `--rename` would end up pointing at the wrong DriveThruRPG listing). A batch-wide default series (from `BatchSeriesModal`) is applied as this form's starting value via `resolve_series()` — a pre-filled, still-editable `Input`, not a field that's silently skipped.

`TagApp._maybe_ask_series()` runs right after `ConfirmScreen` closes, for every path that goes through it (candidate pick, manual override, manual entry): if the confirmed metadata's series is still blank at that point, a dedicated `SeriesModal` dialog asks once more — "Series for {title}: / Leave blank for no series.", mirroring `BatchSeriesModal`'s own convention — before writing. It's a final check, not a first ask: `ConfirmScreen` itself already starts pre-filled with any batch default or match-provided series and lets it be edited freely, so this only fires when it's genuinely still empty.

Outcome lines ("Wrote metadata to X", "Renamed: X -> Y", "Skipped.") are shown via `self.notify()` toasts, not a permanently-visible log widget — Textual's screen stack fully occludes whatever's beneath a pushed screen. Every line is also appended to `TagApp.history` (plain list) so `tests/test_tag_tui.py` can assert on run outcomes without parsing rendered output. The app quits itself the instant a run (or a mid-batch `q`) finishes — no "press q to exit" screen — via `self.exit(message=summary)`; Textual prints that `message` to the real terminal itself, after the alternate screen buffer's already torn down.

**Desktop GUI (`gui_app.py`/`gui_tag_flow.py`):** a PyQt6 app covering every subcommand in one window (Tag/Scan/Review/Write PDFs/All/Preferences; `rename`/`page-labels` via Tag with metadata off — see above), added on request as an alternative to the terminal entirely. Presentation layer only, exactly like `tag_tui.py` — every tab calls straight into `matcher.py`/`review.py`/`pdf_writer.py`/`renamer.py`, none of which know a GUI exists. `cmd_scan()`'s own inline matching loop was factored into `matcher.run_scan_batch()` (progress-callback-aware) specifically so the Scan tab and the CLI share one copy instead of two slowly drifting apart — the only change to existing business logic this feature required; `cmd_scan()`'s printed output is unchanged. This replaced an earlier Tkinter version — see HISTORY.md's "GUI: Tkinter → PyQt6 migration" for why and what was and wasn't carried forward.

Every tab that can block (network calls, pikepdf I/O) runs its work on a background `QThread` via `UiTaskRunner`, whose log lines reach the log `QPlainTextEdit` through a queued Qt signal connection — Qt automatically marshals a signal emitted from a worker thread onto the thread its connected slot's receiver lives on, so there's no polling loop. Only one job per tab runs at a time (the Run button disables itself while busy).

The Tag tab is the interesting case: the actual tagging work (network calls, pikepdf I/O) must run off the GUI thread so the window doesn't freeze, but only the GUI thread may build/exec a `QDialog`. `TagFlowController` (`gui_tag_flow.py`) is a plain, framework-agnostic class — an almost line-for-line port of `TagApp`'s own orchestration methods from `tag_tui.py`, reusing `tag_tui.py`'s pure helpers and result dataclasses directly (`resolve_series`/`build_manual_metadata`/`apply_edits`/`format_candidate_lines`/`do_rename`/`CandidateResult`/`ManualEntryResult`/`ConfirmResult`, none of it reimplemented) — that only needs a `notify(kind, payload, response_q)` callback and a `log(line)` callback, both supplied by `TagWorker` (a `QObject` living on a background `QThread`). Every `await push_screen_wait(...)` in the Textual original becomes a blocking `self._ask(kind, payload)`: it builds a fresh single-slot `queue.Queue`, calls `notify` (which just emits `TagWorker.dialog_requested`), and blocks *only the worker thread* on that queue's `.get()`. `TagTab`'s `_on_dialog_requested` slot — connected with Qt's default auto/queued cross-thread connection, so it always runs on the GUI thread regardless of which thread emitted the signal — builds the matching `QDialog` subclass and calls `.exec()` (Qt's own "block this thread until the modal window closes" primitive), then puts the dialog's `.value` on the response queue, unblocking the worker. `.exec()` blocks the *entire* GUI event loop while a dialog is up, so the window can never be closing at the same moment a dialog request is unanswered.

**`TagWorker.run()` catches any exception from `TagFlowController.run()` and logs it instead of letting it propagate** — a PyQt6 slot running on a `QThread` has no default exception handler, so an uncaught exception there used to abort the whole process rather than just failing the one run (see HISTORY.md's "Robustness pass"). `run_gui()` also installs a `sys.excepthook` backstop for anything that still gets through.

Every checkbox in the GUI (Rename, Page labels, etc.), and the Metadata tagging, Convert images, hyperlink, page-background and back-cover dropdowns, has a short explanatory `_make_hint_label()` underneath it (`gui_app.py`, shared by `WritePdfsTab`/`AllTab` there and `TagTab` in `gui_tag_flow.py`, so the wording for a given flag can't drift between tabs), and the Metadata tagging dropdown shows a link to `https://bookorbit.app/` while BookOrbit is selected, via `_make_link_label()` — a real `QLabel` with rich-text `<a href>` and `setOpenExternalLinks(True)`.

The Review tab is the scan → approve → write-pdfs workflow's approval step done entirely in-GUI instead of a spreadsheet handoff — `review.csv` loaded into one in-memory `list[ReviewRow]` (`rows_by_filename`, the single source of truth) shown in a `QTableWidget`. `status` is editable via `StatusDelegate` (a `QStyledItemDelegate` whose `createEditor()` returns a closed-choice `QComboBox` locked to `Status`'s four values — free text here would silently break `ReviewRow.is_approved()`'s exact string match); `series`/`series_index` need no custom delegate, since `QStyledItemDelegate`'s own default editor for a plain editable cell is already a line edit. Everything else (publisher/authors/tags/product_url/isbn, and a multi-line field for description) is edited via a detail form below the grid, populated on row selection (`currentCellChanged`). Both surfaces write into the same in-memory rows so the grid and the form can't diverge. **`_populate_table()` must `table.blockSignals(True)` around programmatic population** — `QTableWidget.itemChanged` fires for `setItem()` during bulk insert just as it does for a real user edit; omitting this would fire a spurious commit into `rows_by_filename` for every cell of every row on every reload, guarded by `tests/test_gui_app.py`'s `test_review_tab_no_save_during_population`. Every real commit path (an inline table edit, a detail-form field, the description box) also calls `row.mark_edited()`, so `merge_by_filename()` (see below) preserves the edit on a later re-scan even if `status` was never flipped to `approved`.

`gui`'s PyQt6 dependency is an ordinary PEP 723/`uv`/pip dependency — under `uv run --script` (the primary supported path), `uv` resolves and installs it automatically, with no OS-specific install step. `cmd_gui()` still lazily imports `PyQt6`/`gui_app` inside the function body rather than at module level, so a missing GUI dependency only affects `gui`, not every other subcommand — the guard is a short `ModuleNotFoundError` check (for the `requirements.txt`+venv path).

**Preferences (`preferences.py`/`preferences_tui.py`):** a saved API key and DriveThruRPG account name, reachable from both UIs (the `preferences` TUI subcommand and the GUI's Preferences tab) as well as directly editing `data/preferences.yaml`. Saving one here means it now also lives in a plaintext file on disk, not only in an environment variable; `save_preferences()` sets owner-only file permissions (`0600` via `os.chmod`, best-effort — not every platform/filesystem honors it) and the path is gitignored. `resolve_api_key()` has an existing `DTRPG_API_KEY` win over the saved file every time (verified: setting both and calling `build_client()` returns the environment variable's value, not the file's) — the file only matters as a fallback when no environment variable is set. `config.yaml` gained a `preferences:` key (default `data/preferences.yaml`) purely as an overridable *path*, the same pattern as `manual_overrides`/`review_csv` — the actual secret never goes in `config.yaml` itself. The `dtrpg_name` field is currently just stored and shown back in both UIs — not read by any matching/API logic yet — so don't assume it's wired into `DtrpgClient` anywhere; check before relying on it if that changes.

`Preferences` previously also carried five sibling-script paths (one per vendored script below), settable in both UIs, before those scripts were vendored as plain committed files in this project's own directory — there's nothing left to configure for those, so `preferences.py`'s `resolve_path()` (the resolver those five paths used) was removed along with the fields themselves; see HISTORY.md for that transition.

**Logging vs. the alternate screen buffer.** Textual takes over the terminal via an alternate screen; a plain `logging.StreamHandler` writing a `logger.warning()`/`logger.exception()` (already present in `matcher.py`/`dtrpg_client.py`) straight to stderr mid-run would corrupt the display. `main()` configures `logging.basicConfig(handlers=[TextualHandler()])` (from `textual.logging`) instead of the default handler — it checks `active_app.get()` and routes to the running app's own log instead of stderr whenever one is active, falling back to plain stderr when none is, so this is a safe universal replacement, not a `tag`-specific special case.

**DriveThruRPG API is undocumented — treat field-path assumptions as provisional.** `dtrpg_client.py`'s docstring records what's actually confirmed vs. inherited from third-party reverse-engineering; see HISTORY.md's "DriveThruRPG API reverse-engineering notes" for the full detail, but in short:
- `order_products`/`search_library` and the `auth_key`/token auth flow are reverse-engineered from `glujan/drpg` and trusted.
- `products/{id}` (product detail) is a **flat** object in the live API, not the JSON:API envelope an older reference plugin assumed. If matching breaks again with a `KeyError` during product-detail parsing, check `data/debug/` for the raw dump before changing the parser blind.
- Catalog/product-detail endpoints are genuinely public — confirmed via a live, unauthenticated call. Don't add an auth requirement there without re-confirming against a live response first.
- There's no structured "series"/series-index field anywhere in the API; series info lives inside the title text itself, so `ProductMetadata.series` is expected to come from matching/manual overrides, not the client.
- `auth_key` puts the application key in a URL query param, so `resp.url` for that call literally contains it — `_authenticate()`/`_dump_debug()` redact it wherever a URL is dumped or an error message would otherwise embed it.

**Library matches are cheap but thin; catalog matches are rich but rate-limited.** `search_library()` only has title+publisher (that's all `order_products` carries) and does its matching *locally* against a cached full-library pull — no server-side query. `search_catalog()` hits the real search endpoint and enriches every result via a `products/{id}` call immediately (already rate-limited, only ~6 results). Because of this asymmetry, a library-sourced match that's missing a description (or isbn/authors/tags) doesn't mean DriveThruRPG has none — it means nobody's called `DtrpgClient.enrich()` on it yet. `enrich()` is deliberately *not* called on every candidate `search_library()`/`find_candidates()` returns (that would burn the rate limit on options nobody picks); it's called once, lazily, on whichever candidate is actually kept.

**A library entry's `productId` can go stale.** DriveThruRPG can re-list a purchased title under a new product ID after purchase. `DtrpgClient.enrich()` handles this itself: on a failed direct fetch, `_enrich_fallback_by_title()` retries via `search_catalog(meta.title)` and, if found, also overwrites `meta.product_id` with the corrected one. That fallback only accepts a result whose title fuzzy-matches (rapidfuzz `token_sort_ratio` ≥ `_FALLBACK_TITLE_MATCH_THRESHOLD`, currently 70) — it used to blindly trust the first search result, which risked merging a different product's data into a purchased library entry; see HISTORY.md for why 70 (not matcher.py's higher 90 auto-accept bar) was chosen.

Every DriveThruRPG HTTP request goes through a shared `timeout`/retry-with-backoff configuration (`DtrpgClient.__init__`, via `requests.adapters.HTTPAdapter`+`urllib3.util.retry.Retry`) — a stalled connection or a transient 429/5xx no longer hangs or aborts a run outright.

**Image conversion (`image_converter.py`):** ported from a separate personal project (`mac-pdf-rgb-fix`) that fixes CMYK/JPEG2000 images in PDFs for Apple's PDF renderer — ported, not merely called out to, since the two projects don't share a runtime; `convert_images_to_rgb(path)` re-encodes every CMYK/grayscale/JPX image XObject in a PDF to RGB JPEG (Indexed/palette images stay lossless FlateDecode) and saves in place. Uses PyMuPDF (`fitz`) for color-managed CMYK→RGB conversion — Pillow's own CMYK→RGB produces a green cast — and Pillow for JPEG encoding. See HISTORY.md for the source project's ported constraints and how the ordering below was verified.

**Runs before pikepdf ever opens the file for metadata writing, never after — this ordering is deliberate, not incidental**, and applies to every optional pre-write step (image conversion, grayscale conversion, hyperlinking, background-layer tagging). `write_metadata()` runs all of these immediately after the one-time backup, *before* its own `pikepdf.open(...)` block. Each of these other libraries' own save path is different from pikepdf's, and pikepdf's Calibre-specific XMP writing (`_set_calibre_series()` etc.) reaches into private internals to produce a structure real Calibre requires but that "looks right" through any generic reader including these other libraries' own metadata APIs — letting one of their saves happen *after* pikepdf's write would risk the looks-fine-but-silently-breaks failure mode described under "Calibre series bug" in HISTORY.md. Doing all of these first means pikepdf's metadata write is always the last thing to touch the file.

A failure in any of these optional steps is logged and swallowed, not raised — the write still proceeds with metadata-only (matches this function's sidecar-failure convention: losing one piece must not fail a write that could otherwise succeed).

**Vendored-script integrations, `--convert-grayscale`/`--background-layer`/`--remove-background`, plus watermark removal (see below):** unlike everything else in this project, these wrap three plain Python scripts that were separate, independently-authored projects on this machine and are now vendored -- committed as plain files directly in this project's own directory (`convert_pdf_to_grayscale.py`, `castles_and_crusades_background_layer.py`, `remove_dtrpg_watermarks.py`) rather than loaded from a configurable, machine-specific path (see HISTORY.md for why that changed, and what it looked like before). Each wrapper module (`rpg_grayscale.py`/`rpg_background_layer.py`/`watermark_removal.py`) resolves its own script's location as `Path(__file__).parent / "<script>.py"` -- there's nothing to configure, and a missing script (an unreachable state for a normal checkout) produces a clean `*Result(success=False, message=...)`, never a crash. These wrappers and `rpg_hyperlink.py` (below) follow the same shape: a temp-file-then-`os.replace()` atomic swap (the underlying tool can't write back over what it read), and a hidden `.dtrpg-tmp-` prefix on that temp file so a force-killed run can't leave a "book" behind for `scan_pdfs()` to pick up later. **Every one of these swaps (and `image_converter.py`'s) must `shutil.copymode(path, tmp)` before `os.replace()`** — `mkstemp()` creates its file `0600`, and pikepdf/`shutil.copyfile` write *into* that existing file, keeping `0600`, so without this a processed book ends up owner-only (unreadable to a reader app running as another user, e.g. in Docker). Wrapped in `except OSError: pass` — some network filesystems refuse `chmod`, and that must not fail an otherwise-successful step. See HISTORY.md. Still loaded via `importlib.util.spec_from_file_location` rather than a normal `import`, not because of where they live but because of what they are -- independently-authored scripts with their own top-level `main()`/argparse CLI, not modules written to be imported as a library.

**Hyperlinking, `--hyperlink RULES`: one engine, one self-contained rule set per publisher.** `hyperlink_engine.py` is this project's own code (a normal import, not a vendored script). Rule sets live in `hyperlink_rules/`, one module each, named after the file (`hyperlink_rules/gurps.py` is rule set `gurps`), found automatically by `hyperlink_rules.discover()` — no registry to edit. A module that fails to import is reported, not fatal to the others (`python3 hyperlink_engine.py --list` shows both). The engine replaced three separate scripts (`hyperlink_pdf_universal.py` and `hyperlink_pdf_mongoose.py`, vendored from the `gurps_4e_revised_hyperlink` sibling repo, and `hyperlink_pdf_deltagreen.py`), which had drifted: fixes made in one never reached the others. See HISTORY.md for the link-for-link comparisons.
- **The engine owns** everything mechanical: printed number → PDF page (`footer_vote()` — the bottom 45pt, optionally trusting `/PageLabels` that footers confirm; `band_vote()` — top and bottom 10%, one vote per page, like `page_labels.py`), TOC/Index detection strategies, "already linked" checks (`has_internal_links()` counts `LINK_NAMED` too — InDesign exports links as named destinations), reference finders, and `Book.link()`: page range, `search_for()` trimming (a hit must overlap the reference's own words), size sanity, existing-link overlap **checked after trimming** and measured against the *smaller* rect (a publisher's link often covers just the number), optional inset, insert, report row. Saves incrementally and writes `<stem>_link_report.csv` (CSV-injection-safe).
- **`hyperlink_checks.py` owns the cross-book checks** — `book_code()`, `sibling_volume()`, `trigger_word_before()`, `italic_known_title_before()`, `known_title_before()`, `title_after()`, `mixed_case_title_after()`, `title_before_comma()`, `title_in_parentheses()`, `known_title_after()` — each a factory returning a `Check` called as `check(book, pt, ref)`. A check reads per-book state from `book` (`trigger`, `vocab` — this book's own TOC/Index entries, built on first use — `own_title_key`, and the rule set's `known_titles`), so rule sets hold no per-book state and no globals.
- **A rule set is mostly settings**: `class Rules(RuleSet)` setting `page_numbers`, `toc`, `index`, `toc_entries_style`, `toc_linked_when`, `index_skip_if_linked`, `index_numbers`, `reference_style`, `reference_words`, `chapter_refs`, `link_inset`, `trigger_word`, `line_name`, `known_titles`, `other_book_checks`, `chapter_checks` (every option is documented on `RuleSet` itself). Methods can still be overridden for something settings can't express, but a check other publishers could use belongs in `hyperlink_checks.py`. Rule-set modules import only `hyperlink_engine`, never each other. They're Python, run when discovered — only trusted files belong in that folder.
- **`hyperlink_survey.py` drafts a rule set from a publisher's PDFs** (read-only; its trial run works on temp copies). It measures each book with the engine's own strategies (it never re-implements detection, so a draft's choices mean exactly what the engine will do), then `decide()` turns totals into settings, writes `<name>.py` with an evidence comment on every setting, and `<name>_survey.md` with per-book tables, up to 8 sample sentences per cross-book pattern, and a trial run (`hyperlink_pdf()` accepts a `RuleSet` class, not just a name, for exactly this). Hard-won rules in `decide()`, each from a wrong first draft: known titles come only from the surveyed books' own titles and "of the <Title>" phrases that aren't the citing book's own TOC/Index entries — italic phrases before a number are *suggested in the report only*, because publishers italicize their own section names that way too (a first GURPS draft listed "Influence Rolls", "Melee Weapon", … and would have skipped real links); list-style references are chosen when "page"/"pages" dominate, not by list frequency; a capitalized "Page" is skipped only with evidence of in-document pagination — "page N of M", or "Report Page 1" then "Report Page 2" on consecutive pages (a capitalized "Page" ending a line isn't enough: Mongoose headings end "(PAGE 63)"); `page_numbers` defaults to `header_and_footer`, using labels only when a book has a second numbering run. A draft is a starting point: some calls can't be made from a few examples (one ALL CAPS "in THE SENECA WHIRLWIND REPORT" doesn't establish the ALL CAPS convention), so the report's samples are there to be read. `--install` copies into `hyperlink_rules/` and refuses to overwrite.
- **The title-after checks (`title_after()`, `mixed_case_title_after()`) only read past a reference in the same sentence** (`sentence_ends_at()`: "(p. 174). In 1967, U.S. Navy SEALs…" is a new sentence, not a citation), `title_after()` ends a title at punctuation ("(p. 233) in WWI: EWt.") and re-joins hyphenated words, and `mixed_case_title_after()` ignores a "title" with no word starting with a letter ("in 1967"). All found by survey drafts on GURPS books; none changed a link from the hand-written Mongoose or Delta Green rule sets.
- **`title_in_parentheses(codes=…)`** is the Shadowrun Sixth World (Catalyst) convention, added when that publisher was surveyed: the book is named inside the same parentheses as the page number, usually *after* it as a code — "(p. 94 and 96, SR6)", "(p. 124, 6WC)", "(pp. 132-3, Sixth World Companion)" — sometimes before it, "(SR6, p. 72)". Only the rule set's `codes` or `known_titles` count, so "(p. 36, Teamwork Tests)" (a section of this book) stays linked. `name_after_comma()` reads the name for both this check and the survey, so they can't disagree; it skips further page numbers ("p. 161, 179, SR6"), ends at the closing parenthesis even when the PDF glues the next word on ("SR6)for"), or at a period when there's no parenthesis ("p. 133, SR6. Slay…"). `title_key()` reads "&" as "and", so "Hack & Slash" matches "Hack and Slash". Its known-title matching (`known_title_prefix()`, the longest start of the name that's a known title other than this book's own) is shared with **`known_title_after()`**, which catches "p. 283 of Shadowrun, Sixth World" — a title `title_after()` can't (it needs two capitalized words and stops at the comma), safe only because it matches listed titles, never any capitalized phrase. `hyperlink_rules/shadowrun_sixth_world.py` (`--hyperlink shadowrun_sixth_world`) is the installed result of that survey, plus review edits recorded in its docstring.
- **Cross-book checks never apply to Index entries** (only a book-code prefix like "B123" does): an Index entry has no sentence around it, so prose checks only read the neighbouring entry (Mongoose: "Traveller 2" right before "Travel Codes 180"; GURPS: "magic, 34" under Advantages skipped as a citation of *GURPS Magic*).
- **A filename-shaped `/Title`** ("Banestorm Book.qxp", "High Guard Cover.indd") is treated as no title when deriving the trigger word, in every rule set.
- `rpg_hyperlink.py` (`run_hyperlink(path, rules, log)`) runs the engine into a hidden temp file and swaps it in, keeping the `_link_report.csv`. It passes `log` straight through — the old wrapper captured the scripts' `print()`s with `contextlib.redirect_stdout`, which is process-wide and would also capture other threads' output in the GUI. `rule_sets()` lists the rule sets that load (name, label, description) for the UIs.
- **Wiring is generic, so a new rule set needs no UI change:** `write_metadata()`/`write_approved()`/`TagApp`/`TagFlowController` take one `hyperlink: str | None` (a rule-set name). The CLI's `--hyperlink RULES` (shared `add_hyperlink_options()` per subparser) validates the name only when given — via an argparse `type=` function, so other subcommands never import the engine — and keeps `--hyperlink-gurps`/`-mongoose`/`-deltagreen` as hidden `store_const` aliases in the same mutually exclusive group (two different choices are an error, not "last wins"). The GUI's Tag and Write PDFs tabs share `_add_hyperlink_picker()` (`gui_app.py`): "Off" plus every rule set, `currentData()` being the name; its hint shows the selected rule set's `description` as plain text. `tests/test_gui_app.py`'s `test_hyperlink_picker_lists_rule_sets_and_passes_choice` guards that the *name*, not the label, reaches `write_approved()`.
- **Delta Green specifics** (`hyperlink_rules/deltagreen.py`, measured across 10 real books): references use the word **"page"/"pages"** ("See COMBAT on page 48", "(page 164)", "pages 12–13"). An **ALL CAPS** section name next to the reference means this book and is linked; a **mixed-case/italic title** ("page 85 of the *Agent's Handbook*", "see the *Handler's Guide*, page 312") means another book and is skipped unless it's this book's own title — titles hyphenated across lines are re-joined first. Capitalized "Page"/"PAGE" and "page N of M" are skipped (in-fiction handout pagination). The TOC and Index are each linked only if they have no internal links (every one of the 10 test books already had a TOC linked with named destinations). Index numbers in the header/footer band are linked except the page's own printed number; link boxes are trimmed 12% top and bottom because tightly set index lines otherwise overlap.
- `rpg_grayscale.py` (`convert_pdf_grayscale()`) shells out to the real Ghostscript binary (`gs`) via the vendored script's non-interactive `run_ghostscript()`/`restore_metadata_and_labels()` functions (bypassing its interactive `main()` prompt, always converting everything including covers) — needs Ghostscript on PATH, a system package PEP 723/uv/pip can't provide; a missing `gs` produces a clean, actionable message.
- `rpg_background_layer.py` (`apply_background_layer()`) invokes the vendored script as a real `subprocess` (`sys.executable src dst [--remove]`), since — unlike the other two — it has no separable non-interactive function to import; its whole logic lives inside an `argparse`-driven `main()`. Has a `SUBPROCESS_TIMEOUT_SECONDS` (300s) timeout so a genuinely hung child process can't block a run forever. Tags each page's full-page decorative background as a toggleable Optional Content Group layer, or deletes it outright — for Troll Lord Games PDFs (Castles & Crusades) only.
- `watermark_removal.py` (`detect_watermark()`/`remove_watermark()`) loads the vendored script's already-factored-out `collect_lines`/`detect`/`scan`/`strip_from_streams` functions via `importlib.util.spec_from_file_location`, and reimplements its `main()`'s post-confirmation removal sequence directly against them (that part was never factored into its own function upstream) — see "Watermark detection/removal" below for why this one is a fundamentally different kind of integration from the other two.

**Watermark detection/removal, `tag` only, no CLI flag/GUI checkbox — a hidden feature:** deliberately not described in the README, the CLI usage notes or release notes (the user's choice); keep it that way when editing user-facing docs. It runs automatically, as literally the first thing `TagApp._process_one()`/`TagFlowController._process_one()` do for each file — before matching, before anything else. If a watermark is detected (a line repeating in the lower-left corner of most pages — auto-detect mode only, never the vendored script's free-text search, since there's no prompt in this project's own flow to forward a search string through), a Yes/No modal/dialog (`WatermarkModal` in `tag_tui.py`, `WatermarkDialog` in `gui_tag_flow.py`) shows the detected text and page count and asks before removing anything — worded as a *possible* watermark via the shared `watermark_removal.describe_detection()` (a publisher's own copyright footer can pass the same repetition test, and under `WEAK_EVIDENCE_PAGE_COUNT` pages almost any corner line does); the text is shown as plain text in both UIs since it comes from inside the PDF; declining leaves the file untouched and the rest of the flow proceeds normally. No on/off flag or configuration at all — the vendored script always ships with this project, so the per-file Yes/No confirmation is the only control, matching "ask the user" being the whole point of this feature. Runs before every other pre-write step (image conversion, hyperlinking, grayscale, background-layer) for the same "non-pikepdf steps must run before pikepdf's own metadata write" reasoning documented above, and before matching too, so there's no window where a later step could run against a still-watermarked file. Not available on `write-pdfs`/`all` — those are non-interactive batch paths with no way to ask the user anything, the same reason candidate-pick/manual-entry/series-prompt are `tag`-only too.

**Page labels (`page_labels.py`):** written by this project's own code, not a vendored script — it started from `fix_page_labels.py` in the `gurps_4e_revised_hyperlink` sibling repo, but that's an interactive wizard, reads footers only, and counts arabic pages up from "printed page 1", which can't represent a book whose cover is counted as page 1 (Call of Cthulhu). The model instead: one page-number *offset* per book (physical index minus printed number), voted per page over every digit-only word in the top and bottom `BAND_FRACTION` (10%) of each page, so header- and footer-numbered books both work. Every page's label comes from that offset: covers (PDF page 1 and the last page, unless that page itself shows an agreeing number) are "Cover", with three exceptions: when PDF page 2 has no agreeing number and a retail barcode (`page_render.page_has_barcode()`), page 2 is the back cover and the last page is numbered normally (SJG, Delta Green, Evil Hat layouts; the last page there is an ad or a form); a landscape page 1 in a portrait book (`is_wraparound()`, Shadowrun Sixth World) means there's no back cover; and a blank white last page (`page_is_blank()`) isn't one either. The last-page rule deliberately does *not* require a barcode: on the corpus, ~70 barcode-less last pages were real back covers versus ~45 non-covers (dividers, ads, maps), so requiring one would do more harm than good. Otherwise, pages before printed page 1 are sequential lowercase roman, and everything else is its printed number, including unnumbered pages and pages before the first visible number. Vote **per page, not per digit** — a 10% band also catches table values, years and product codes, which swamp a per-digit vote. It refuses (returns a reason, leaves existing labels untouched) on weak agreement, agreeing pages spanning under half the book (boxed sets), or a competing offset with its own following (merged multi-volume PDFs). Those thresholds were tuned on 490 real RPG PDFs; see HISTORY.md before changing them. Many publisher PDFs carry `/PageLabels` that are just physical page numbers (cover = "1"), so existing labels aren't ground truth.

Labels live in the document catalog, not metadata, so `write_metadata()` sets them inside its own final pikepdf save (after every pre-write step, which is when detection runs), and `--metadata bookorbit`'s metadata wipe doesn't touch them. With `--metadata off`, labels are the only thing that save writes, with `fix_metadata_version=False` (below). The standalone path, `pdf_writer.write_page_labels_only()`, saves with **`fix_metadata_version=False`** — pikepdf's default re-serializes the entire XMP packet on every save (verified: a labels-only save reformatted three books' XMP), and a labels-only write must not re-serialize a tagged file's Calibre XMP (the "Calibre series bug" risk). It lives in `pdf_writer.py`, not `page_labels.py`, so the one-time `backup()` rule stays in one module.

**Page rendering and barcode detection (`page_render.py`):** everything that renders a PDF page lives here and runs in a child process (the barcode and blank-page checks, and `render_page_png()` thumbnails for tag's back-cover prompt). Barcode detection is two independent checks on one 300 DPI render, either sufficient — `_repeating_stripes()` (a dense stripe band whose whole 1.6in window repeats for ≥0.2in: strict, and it catches barcodes that are a blurry part of a flattened cover image, like Delta Green's) and `_decodes_ean13()` (a real EAN-13/UPC-A decode with a valid check digit, seen on **≥5 rows** — line art passes the checksum on 1-2 rows by chance, real barcodes decode on 11-132). Measured on page 1/2/middle/last of 490 books: 0 middle-page hits, 75 page-2 and 150 last-page hits, every one visually confirmed a real back cover, and never both page 2 and the last page in one book. **Rendering can abort the whole process** (MuPDF hits an abort on one real Traveller PDF's last page at every DPI, including the latest PyMuPDF), which Python can't catch — so callers use `page_has_barcode()`/`page_is_blank()`/`render_page_png()`, which run in a child process (`sys.executable` on this module's own `__main__`) with a timeout, returning None on a crash. Never call `has_barcode()`/`is_blank()` directly from `tag`/GUI/write paths. Poster-sized pages (over `MAX_PIXELS` at 300 DPI) are skipped outright.

**Back cover moves (`back_cover.py`):** `--back-cover-to-page-2`/`--back-cover-to-end`. `locate_back_cover()` only answers automatically on positive evidence: a wraparound page 1 means no separate back cover; otherwise whichever of page 2 and the last page has a barcode, and both means nothing moves (moving the wrong page is much worse than moving nothing — e.g. books with no back cover end on an index, a blank page or a divider). **PDF-only releases usually have no barcode**, so with none, `locate_back_cover(path, to)` also returns a `candidate` (the last page for "page-2", page 2 for "end"; never a blank page), and **`tag` asks** — `BackCoverModal` in the TUI (text snippet plus an "Open page" button that opens a child-rendered thumbnail in the system viewer, since a terminal can't show images) and `BackCoverDialog` in the GUI (front cover and candidate thumbnails side by side), both worded by the shared `describe_question()`. Because only tag can ask, **tag does its own move** (`TagApp`/`TagFlowController._maybe_move_back_cover()`: locate → ask if needed → `backup()` → `move_back_cover(path, to, index, reason)`) right before `write_metadata()`, and doesn't pass the back-cover flags to it — the same "backup before a pre-write change" pattern as watermark removal. `write-pdfs`/`all` go through `write_metadata()`'s own back-cover step (first among the pre-write steps, right after the backup), which is barcode-only and logs a pointer to tag when it skips a barcode-less book. Either way the move happens before every other pre-write step and before page-label detection. The move is pikepdf `del pages[i]` + `insert`/`append` of the same page object, so bookmarks and links keep pointing at the same pages (verified: 24 bookmarks and 81 links on a hyperlinked book, both directions). Existing `/PageLabels` are position-based, so `read_existing_labels()`/`write_existing_labels()` (in `page_labels.py`, using `pikepdf.NumberTree`) decode them per page and rewrite them in the new order — round-trip verified identical on 20 real labeled books. PyMuPDF's own `get_label()` misreads UTF-16 label prefixes (e.g. `<FEFF0043…>1` for "COVER1"), so don't use it as ground truth for labels. Saves are atomic, keep file permissions, and use `fix_metadata_version=False`.

`--convert-images`/`--convert-grayscale` are mutually exclusive (opposite operations on the same images), as are `--background-layer`/`--remove-background` (opposite operations on the same background) and `--back-cover-to-page-2`/`--back-cover-to-end` — enforced at both layers: `argparse`'s `add_mutually_exclusive_group()` per subparser (`write-pdfs`/`all`/`tag`, a separate group instance each — groups don't span parsers), and in the GUI — the image conversions as one "Convert images" dropdown (`_add_convert_images_picker()` in `gui_app.py`: Off/RGB/Grayscale, shared by the Tag, Write PDFs and All tabs), the background pair as one "Page background" dropdown (`_add_background_picker()`: Off/Layer/Remove, Tag and Write PDFs tabs), and the back-cover pair as one "Move back cover" dropdown (`_add_back_cover_picker()`: Off/To page 2/To the end, all three tabs). A dropdown can't hold both choices of a pair, so the GUI needs no extra wiring. `write_metadata()`/`write_approved()` don't enforce this themselves — they just run whichever step(s) they're told to. The GUI's hyperlink and page-background dropdowns exist only on the Tag and Write PDFs tabs (not All) since they're publisher-specific, not general features — the CLI options themselves are still present on all three subparsers purely because `cmd_all()` shares `cmd_write_pdfs()`'s own `args` namespace.

**Embedded PDF metadata targets Calibre's own format, verified against a real installed Calibre 9.13 — not guessed, and not just "round-trips through pikepdf."**
- `dc:creator`/`dc:publisher` both get the **publisher** name, not DriveThruRPG's actual author list — deliberate policy (DTRPG's per-book author credits are too inconsistent to trust for this library).
- `dc:description` → Comments, `dc:subject` → Tags, both filtered through `TAG_BLOCKLIST` in `dtrpg_client.py` for the latter.
- `pdf_writer._set_calibre_identifiers()` writes `xmp:Identifier` (dtrpg + isbn) via pikepdf's private XMP internals (`_xmp_doc`, `_get_rdf_root`) — there's no supported public-API way to write a qualified/structured XMP property (`rdf:parseType="Resource"`), and Calibre's own reader (`calibre/ebooks/metadata/xmp.py`) requires exactly that shape. Guarded by `except AttributeError` in case pikepdf's internals change.
- `pdf_writer._set_calibre_series()` exists for the same structural reason: `calibre:series` must wrap its value in a nested `rdf:value`, and the index is a *differently-namespaced* child (`calibreSI:series_index`, URI `http://calibre-ebook.com/xmp-namespace-series-index`) nested inside the series element, not a sibling `calibre:series_index` property — see HISTORY.md for the bug this fixed. `series_index` is only written when actually known (empty/non-numeric `row.series_index` omits the `calibreSI:series_index` element rather than defaulting to `1.00`) — Calibre's own `read_series()` also defaults a missing index to 1.0, so this doesn't change what Calibre displays, it just avoids fabricating a false "confirmed #1" in the raw data.
- ISBN validity is checked before writing (`sidecar_writer._split_isbn()`, imported into `pdf_writer.py`) — a `row.isbn` that isn't 10 or 13 digits gets skipped with a warning rather than written unconditionally under a scheme readers will trust as a real ISBN.
- `_get_or_create_rdfdesc()` is shared by both private-internals writers and by the series-clearing `else` branch below — reuses the one `rdf:Description[@rdf:about=""]` block pikepdf's own public API writes into, rather than creating a second one; all three call sites are guarded by `except AttributeError`.
- `pdf:Keywords` also gets the tags list (joined with `"; "`) — pikepdf's docinfo sync maps the classic `/Keywords` Info-dict field from `pdf:Keywords` specifically, not from `dc:subject`. Docinfo sync separately maps `/Subject` from `dc:description`, not from `dc:subject` — don't conflate Subject and Tags.
- Any reader that implements Calibre-compatible XMP parsing picks this up too — confirmed for Kavita's own `PdfMetadataExtractor.cs`, which reads the exact nested structure `_set_calibre_series()` writes. One confirmed gap: Kavita's PDF path looks for `pdfx:isbn`/`prism:isbn`, neither of which this project writes (ISBN lives in Calibre's own `xmp:Identifier` Bag instead), so ISBN doesn't carry over to Kavita.
- One deliberate exception to "Calibre format only": `bookorbit:seriesName`/`bookorbit:seriesIndex` also get written, in BookOrbit's own simple scalar form — see the BookOrbit sidecar section below for why.
- **Re-tagging a file clears stale series data, not just adds new data.** `write_metadata()` edits a PDF's *existing* persisted XMP tree in place (unlike `sidecar_writer.py`, which fully regenerates its output each run). When the current match has no series, an explicit `else` branch clears all four series-related properties (`calibre:series` and its nested index, plus both `bookorbit:` fields) rather than leaving stale data from a previous match in place; `bookorbit:seriesIndex` is explicitly deleted whenever the current match has a series but no numeric index.

**Sidecar files (`sidecar_writer.py`) target BookOrbit's and Grimmory's own real formats, each verified against that app's actual open-source parser/writer — not guessed:**
- BookOrbit `.opf`: standard EPUB2/Calibre-style OPF; series via the same `<meta name="calibre:series">` convention Calibre itself uses (plain `name`/`content` attributes, no namespaced element/nested-value structure needed); ISBN auto-bucketed into isbn10/13 on BookOrbit's end from one `<dc:identifier opf:scheme="ISBN">`.
- **The `.opf` sidecar's series data is unreachable by BookOrbit in practice**: BookOrbit's default `metadataPrecedence` for PDFs tries `embedded` first and only falls through to `opfFile` if `embedded` returns *nothing at all* — a whole-source fallback, not a per-field merge. And BookOrbit's PDF reader returns something for *every* PDF it can open (`pdf-parser.ts`'s `parsePdfBuffer()` has no empty case; with no metadata, a filename-derived title and the page count), so with the default order `opfFile` is **never** opened for a PDF — not even a wiped one. This is why BookOrbit's series fields are also written directly into the embedded PDF, and why **the `.opf` is written only under `--metadata bookorbit`, which needs the BookOrbit library's metadata precedence (a per-library setting) changed to put OPF file ahead of Embedded** — every user-facing description of that mode says so. It also strips **all** PDF-level metadata (the full XMP packet *and* the classic Info dictionary) so nothing in the PDF disagrees with the `.opf`, and writes no `.metadata.json`. The wipe was originally meant to make BookOrbit fall through to the `.opf` under the default order; that was reasoned from the scanner loop alone, never tested in a real scan, and is wrong — see HISTORY.md. Re-tagging in another mode after a BookOrbit write deletes the stale `.opf` rather than leaving it, and vice versa for `.metadata.json`.
- Grimmory `.metadata.json`: schema from the actual Java DTOs in `github.com/grimmory-tools/grimmory`. Unlike the OPF, isbn10/isbn13 are separate flat fields with no auto-detection on Grimmory's end, so `sidecar_writer._split_isbn()` buckets by digit count itself.
- Both are best-effort: a field with no data is just omitted, matching how each app's own writer behaves. `pdf_writer.write_metadata()` calls the Grimmory writer only for `metadata="grimmory"` and the BookOrbit `.opf` writer only for `"bookorbit"`, both after the embedded-PDF write succeeds, and catches `Exception` broadly around each — a sidecar failure is logged, never raised.

Don't reshuffle any of this mapping without checking the relevant module's docstring and the real app source first — it reflects explicit, verified choices, not defaults.

**Backups are one-time, not per-run.** `pdf_writer.backup()` only creates a `.bak` if one doesn't already exist, so the backup always represents the pre-tagging original even across repeated re-tagging runs — it must not be refreshed on every write. It's public because watermark removal (which runs before `write_metadata()` and its own backup call) must call it first in both `tag_tui.py` and `gui_tag_flow.py`; if the backup fails, the watermark is left in place. Any future step that modifies a file before `write_metadata()` needs the same treatment.

**`renamer.py`'s `_sanitize_component()`** replaces `/`+NUL (illegal on a native Unix filesystem) and the Windows/SMB-reserved set (`\:*?"<>|`, in case the library is ever accessed over SMB/exFAT/a Windows-formatted drive) with `-`. A colon followed by whitespace is special-cased to `" - "` first (`"Title: Subtitle"` → `"Title - Subtitle"`, not `"Title- Subtitle"`) since that's the overwhelmingly common shape a colon takes in an RPG title — any other colon (none, or no trailing space) still falls through to the general substitution and becomes a bare hyphen. This is a real path-traversal defense, not just filesystem-legality cleanup: `title`/`series` feed directly into a filesystem path, and both ultimately trace back to DriveThruRPG's *public* catalog — because `/` is always one of the replaced characters (and `Path.with_name()` independently rejects any component containing a separator), a crafted title/series like `../../../../tmp/x` can never place a file outside the target directory; it just becomes a harmless literal string. Re-verify this (see HISTORY.md for how) if this character set ever changes again, or if `renamer.py`'s filename-building logic is ever duplicated elsewhere instead of reused (as `--rename` deliberately does via `_rename_one()`).

**`review.py`'s CSV merge preserves user edits.** `merge_by_filename()` preserves an existing row over a freshly-matched one for the same filename when the existing row is `approved`, **or** when `ReviewRow.edited` is set (see "Desktop GUI" above for where that gets set) — re-scanning must not clobber a manual correction just because its status was never flipped to approved. `load_review()`/`save_review()` also coerce a short/hand-edited CSV row's missing fields to `""` rather than `None`, and write atomically (temp file + `os.replace()`) so a crash mid-write can't truncate the file.

**`review.csv` is a CSV/formula-injection target, not just a local file.** `matched_title`/`description`/`publisher`/`tags` are sourced from DriveThruRPG's *public* catalog — anyone can list a product there — and the documented `scan`/`write-pdfs` workflow has the user open `review.csv` by hand in a spreadsheet app. A crafted catalog listing title starting with `=`/`+`/`-`/`@` would be read as a formula by Excel/LibreOffice/Numbers. Fixed with the standard leading-apostrophe defang on write (`_defang_formula`) and a matching strip on read (`_refang_formula`), so the safety prefix never leaks into what actually gets written into a PDF. Both functions pass non-`str` values through unchanged (see HISTORY.md for the crash this avoids).

**The GUI's confirm/series dialogs force plain text for any catalog-sourced value shown in a `QLabel`** (`_plain_label()` in `gui_tag_flow.py`, forcing `Qt.TextFormat.PlainText`) — `QLabel` otherwise auto-detects and renders markup as real rich text/HTML (`Qt::AutoText`), and `meta.title`/`meta.authors_str()` are attacker-reachable DriveThruRPG catalog content on the one screen whose entire purpose is showing the user exactly what's about to be written. `QLineEdit` fields and `QListWidgetItem`s were never at risk (neither has a rich-text mode) — only bare `QLabel`s needed this. Filenames get the same treatment (a real one in this library is `Sword Worlds [OCR].pdf`).

**The terminal UI (`tag_tui.py`) has the same rule, with Textual's own `[...]` markup instead of HTML:** any `Label`/`Static` or `notify()` showing a filename, catalog title/authors, or watermark text must pass `markup=False`, and candidate-list `Option`s wrap their prompt in Rich's `Text()`. Without it, `Sword Worlds [OCR].pdf` displays as `Sword Worlds .pdf`, and any `[/]` in the text crashes the app with `MarkupError`. `notify(markup=...)` needs Textual 4.0+, hence the `textual>=4.0` floor. Fixed strings (button labels, prompts) don't need it.

**`matcher.scan_pdfs()` skips dotfiles** (macOS writes a hidden `._<name>.pdf` AppleDouble sidecar next to every real file on a filesystem without native resource-fork support — common on SMB/exFAT shares — and it matches `*.pdf` just as well as the real file). **`pdf_writer.write_approved()` looks files up by name via a plain `{name: Path}` index built once from `scan_pdfs()`**, not `root.rglob(row.filename)` per row — a filename is a literal string here, not a glob pattern (a real name containing `[`/`*`/`?` used to either match nothing or the wrong file); a duplicate filename found in two different subfolders is warned about once rather than silently resolved by whichever one `os.walk()` happens to see first. It also catches any exception per file (not just `pikepdf.PdfError`/`OSError`) and records it as a failed `WriteResult` rather than letting it abort every remaining file in the batch.

# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A pipeline that matches local RPG PDF filenames against DriveThruRPG metadata (purchased library, then public catalog, then manual overrides) and writes the result three ways: into each PDF's embedded XMP metadata in Calibre's format, plus a BookOrbit `.opf` sidecar and a Grimmory `.metadata.json` sidecar next to it (see `sidecar_writer.py`). There is no database and no long-running service — it's a CLI run manually against a folder of PDFs. History: Kavita, then BookOrbit-only embedded XMP, were both tried and superseded — current policy is Calibre-format embedded metadata (universal, not reader-specific) plus per-reader sidecars for apps with their own sidecar convention. `kavita_client.py` was deleted as dead code once Kavita was dropped.

## Setup and running

No `pyproject.toml`/`setup.py` — this is a flat script directory, not a packaged/installable project. `dtrpg-metadata-download.py` carries its own dependency list as [PEP 723](https://peps.python.org/pep-0723/) inline script metadata (the `# /// script` block at the top) and is executable directly — no manual venv:

```bash
export DTRPG_API_KEY=...   # Application Key from the DriveThruRPG account page, NOT the account password
./dtrpg-metadata-download.py <subcommand>
```

`uv` resolves and caches the dependencies (pikepdf/rapidfuzz/PyYAML/requests/lxml/textual/pymupdf/pillow/PyQt6) transparently on first run via the shebang (`#!/usr/bin/env -S uv run --script`); every run after that is instant, no `.venv` involved. `requirements.txt` + a classic `python3 -m venv .venv && ./.venv/bin/pip install -r requirements.txt` still works too, for anyone without `uv` — keep both in sync if dependencies change. Subcommands:

- `tag PDF_PATH` / `tag --root DIR [--bookorbit-mode] [--rename]` — a full-screen Textual TUI (`tag_tui.py`), no review.csv, both for a single file and for --root's per-file loop (one code path, not two). This is the primary/actively-used path. See "Interactive UI (`tag_tui.py`)" below for the screen-by-screen design; the CLI surface here (`tag_parser`'s flags, guard clauses) is unchanged from before the TUI rewrite — `cmd_tag()` is a thin dispatch that constructs and runs a `TagApp`.
- `scan --root DIR [--refresh-library] [--apply-review]` → `write-pdfs --root DIR [--bookorbit-mode]` — batch path gated by `data/review.csv`: `scan` matches everything and writes rows to the CSV (never auto-writes PDFs), you hand-edit `status` to `approved`, then `write-pdfs` applies only approved/auto-accepted rows. `all` runs both in sequence.
- `review-status` — prints CSV status counts.
- `rename PDF_PATH` / `rename --root DIR [--dry-run]` — renames each already-tagged PDF (plus its `.bak`/`.opf`/`.metadata.json`) to `<series> - <title>.pdf`, reading title/series back from the `.metadata.json` sidecar rather than the embedded XMP (see `renamer.py`'s docstring — Calibre's/BookOrbit's embedded series fields are structured XMP properties that can't be read back reliably through pikepdf's public API, same limitation the writer has). Untagged files and files already named correctly are skipped; a computed name that collides with an existing file is left alone and reported as failed, never overwritten. Renames a file's whole companion group atomically-ish — a mid-group OS failure rolls back whatever already succeeded rather than leaving `.pdf`/sidecars split across old and new names.
- `--bookorbit-mode` (on `tag`/`write-pdfs`/`all`) — see the BookOrbit sidecar section below; flips the embedded-PDF-vs-`.opf` tradeoff instead of writing Calibre metadata.
- `--convert-images` (on `tag`/`write-pdfs`/`all`) — converts CMYK/grayscale/JPEG2000 images in the PDF to RGB JPEG via `image_converter.py`, before metadata is written. See "Image conversion (`image_converter.py`)" below.
- `gui` — a desktop GUI (PyQt6, `gui_app.py`/`gui_tag_flow.py`) covering every subcommand above in one window, including an editable table for `review.csv` instead of hand-editing it in a spreadsheet. See "Desktop GUI" below for the architecture. PyQt6 is a normal dependency (installed automatically via `uv run --script`, same as every other dependency here) — no system-level prerequisite, unlike the Tkinter version this replaced.
- `preferences` — view/edit a saved API key and DriveThruRPG account name (`preferences_tui.py`; also a Preferences tab in the GUI). See "Preferences" below.

`config.yaml` supplies defaults (root, thresholds, cache paths); CLI flags override it. Copy/edit it per-machine — it's meant to stay free of secrets. The API key comes from `DTRPG_API_KEY` if set, or otherwise from `data/preferences.yaml` (gitignored, owner-only file permissions) — see "Preferences (`preferences.py`/`preferences_tui.py`)" below for the security trade-off this deliberately takes on, and why the environment variable still wins when both are present.

**Match precedence** (checked in this order, in both `tag` and `scan`, via `matcher.match_file()`/`_tag_one()`): `data/manual_overrides.yaml` (full hand-typed metadata, for titles not on DriveThruRPG at all) → `<root>/dtrpg_urls.csv` (just `filename,drivethrurpg_url` — lives alongside the PDFs it describes, not in `data/`; full metadata is fetched live via `DtrpgClient.get_product()`; auto-approved with no confirmation prompt even in `tag`, falls back to search if the fetch fails) → purchased library → public catalog.

**`load_manual_overrides()` used to crash outright on a plausible hand-edit mistake.** It read each field with `meta.get(key, default)`, but that default only applies when the *key is missing* — an entry with a key present but blank (e.g. `source:` with nothing after it) parses to an explicit YAML `null`, which `.get()` happily returns as-is instead of falling back. Most fields just ended up silently wrong (`None` instead of `""`), but `source` went through `Source(meta.get("source", Source.MANUAL.value))` and crashed with `ValueError: None is not a valid Source` — taking down `tag`/`scan` entirely until the file was fixed, since this loader runs unconditionally at the start of both. The mistake is a plausible one specifically *because* most other fields in the documented template (`description: ""`, `product_url: ""`, etc.) genuinely are meant to be left blank, so a user has no obvious reason to treat `source:` differently. Fixed by switching every field to `meta.get(key) or default`, which treats an explicit `null` the same as a missing key.

## No test suite (with two scoped exceptions)

There's no pytest/unittest scaffolding and no lint config in this repo. Verification during development has been done with ad hoc inline Python scripts: build a throwaway PDF with `pikepdf.new()`, run it through `matcher`/`pdf_writer` with a `unittest.mock.MagicMock()` standing in for `DtrpgClient` (to avoid live API calls), then reopen the PDF and assert on what was actually written — not just that the code ran without raising. When the real API's response shape needs checking, `data/debug/*.txt` dumps (raw response bodies, written automatically on any parse failure — see below) are the source of truth; prefer replaying a real captured dump over guessing at shape from third-party code.

**`tests/test_tag_tui.py` is the one committed exception, added deliberately when `tag` was rewritten as a Textual TUI.** `tag_tui.py`'s screen/message wiring (widget IDs, `push_screen_wait()` sequencing, which screen a given result routes to next) is meaningfully more failure-prone than the `print()`/`input()` code it replaced — a wrong widget id or a dropped `await` silently breaks a whole interactive path in a way that's easy to miss reading the code and easy to never notice by hand (you'd have to click through every path, every time, to catch a regression). It's a plain script, not a pytest suite (`./tests/test_tag_tui.py`, no framework/fixtures beyond `Textual`'s own `App.run_test()`/`Pilot`), matching this project's "runnable script, not a framework" convention even in the one place it now has committed tests. **It already caught two real bugs during development, not just theoretical ones:** (1) `ManualEntryScreen`'s Submit button falls below the visible screen area on a standard-size terminal once the form has enough fields (Title through Product URL plus the Description text area) — `pilot.click("#submit")` failed with `OutOfBounds`, a real usability problem a click-only design would have hit for real users too, not just the test. Fixed by adding a `ctrl+s` keybinding that submits regardless of scroll position. (2) The first draft of `TagApp._manual_entry()` wrote directly after `ManualEntryScreen` submitted, skipping the "About to write: {title}" / confirm step every other path (candidate-pick, manual override) goes through — a real behavioral regression from the old `_manual_entry_flow()`, which always double-confirms even after manual entry. Caught because the test asserted on a `ConfirmScreen` widget id that turned out not to be on screen; fixed by routing manual entry through the shared `ConfirmScreen` too.

**`tests/test_gui_app.py` is the other committed exception, added deliberately alongside the GUI, for the same reason as `tests/test_tag_tui.py`: the request/response protocol between `TagWorker`'s background `QThread` and `TagTab`'s main-thread dialogs is exactly the same class of easy-to-get-subtly-wrong wiring.** Uses `PyQt6.QtTest.QTest` for widget interaction rather than `pytest-qt` — this project has zero test-framework dependencies by deliberate convention, and `QtTest` ships inside PyQt6 itself, so introducing one wasn't needed here either. Controller-only tests drive `TagFlowController` directly with a scripted fake `notify` callback (no real widgets, no display needed, and no Qt import at all — `TagFlowController` is framework-agnostic); a handful of tests build the real highest-value dialogs and exercise the Review tab's table directly, both needing the one shared `QApplication` instance (Qt permits exactly one per process). One test (`test_tag_worker_signal_round_trip`) drives a *real* `QThread` end-to-end through the signal-based `_ask()` path — the single highest-novelty piece of the Tk→Qt migration, so it gets direct coverage beyond the fake-`notify` group. Another (`test_review_tab_no_save_during_population`) guards a real Qt-specific gotcha with no Tkinter analog: `QTableWidget.itemChanged` fires during programmatic bulk population just as it does for a real user edit, so `ReviewTab._populate_table()` must `blockSignals(True)` around it or every reload fires spurious commits.

**This test suite replaced an earlier Tkinter-based one, ported alongside the GUI rewrite (see "Desktop GUI" above for why).** The old suite's highest-value caught bug — `ttk.Treeview.identify_column()` disagreeing with `.bbox()` about column boundaries, misrouting clicks to the wrong column — has no Qt equivalent: `QStyledItemDelegate` editor placement is entirely Qt-internal, so there's no manual hit-testing left to get wrong, and the ported Review-tab test is now a plain persistence smoke test rather than a hit-testing regression guard. A separate Tcl/Tk-specific `after()`-timer-during-`wait_window()` quirk that constrained how the old suite scheduled auto-interaction likewise has no Qt equivalent and wasn't carried forward.

**The candidate screen's "Pick" button/action never used the URL field, in both the TUI and the GUI — reported by the user, not caught by any test, since every existing test either picked a candidate or used the URL field, never both at once.** Pasting a URL and clicking Pick (a very natural thing to try) silently ignored the pasted text and used whatever was highlighted in the candidate list instead. Fixed by adding a dedicated **Use URL** button/action in both UIs, wired to the exact same submit logic Enter already used (`CandidateScreen._submit_url()` in `tag_tui.py`; `CandidateDialog._submit_url()` in `gui_tag_flow.py`) — Pick and Use URL are now unambiguously separate actions in both places, guarded by `tests/test_gui_app.py`'s `test_show_candidate_dialog_use_url_button`. Adding the TUI's button surfaced a second real bug: putting it in a `Horizontal()` alongside the full-width URL `Input` pushed it to `x=74` in an 80-column terminal (`Input` claims available width greedily) — clipped past the edge and unclickable, the same class of bug as `ManualEntryScreen`'s previously-documented off-screen Submit button, just horizontal instead of vertical. Fixed by moving Use URL into the row of standalone buttons below the `Input` instead, where it and Manual entry/Skip/Quit all fit comfortably (confirmed by checking each button's actual computed `Region` in a real `run_test()` session, not just by eyeballing the CSS).

**Reading back with `pikepdf.open(...).open_metadata().get(...)` is not sufficient on its own for Calibre-specific structured fields — this is exactly how the series bug (below) went undetected for most of this project's history.** A malformed `calibre:series` write can round-trip through pikepdf perfectly (pikepdf will happily read back whatever it wrote) while being completely invisible to the real target app, which parses the raw XMP independently and can have structural requirements pikepdf's generic reader doesn't enforce. For anything Calibre-, BookOrbit-, or Grimmory-specific, verify against the real thing: `ebook-meta`/`ebook-meta --to-opf` (Calibre is installed locally) on a PDF this project actually wrote, or — for BookOrbit/Grimmory — fetch that app's real open-source parser and run it directly via `npx tsx` against a generated file (see the BookOrbit `.opf`/XMP verification done this way earlier; `pdf-lib`/`fast-xml-parser` are the only npm deps needed). A field that "looks right" only by pikepdf's own reading of its own write has not actually been verified.

## Architecture

**Module chain:** `dtrpg_client.py` (network + caching) → `matcher.py` (filename→query, fuzzy scoring, decides `ReviewRow`/candidate list) → `review.py` (CSV I/O, only used by the batch path) → `pdf_writer.py` (writes XMP via pikepdf, then calls `sidecar_writer.py` for the `.opf`/`.metadata.json` files) → `dtrpg-metadata-download.py` (CLI, wires it all together). `provenance.py` holds the two shared types (`ProductMetadata`, and the `Source`/`Status` enums) that every other module imports. `renamer.py` is a separate, independent leaf off the CLI — it runs *after* tagging, reading back already-written metadata from the `.metadata.json` sidecar to rename files, rather than participating in the match/write chain itself. `tag_tui.py` is `tag`'s presentation layer — it calls into `matcher`/`pdf_writer`/`renamer` exactly the way `dtrpg-metadata-download.py` itself does for every other subcommand, and none of those modules know or care that `tag` is a TUI rather than `print()`/`input()`.

**Interactive UI (`tag_tui.py`):** a Textual app, added specifically so manual metadata entry could have a real multi-line text area for Description (`input()` can't do that) — see the module's own docstring for the full screen-by-screen mapping from the old `_tag_one()`/`_manual_entry_flow()`/`_prompt_manual_metadata()` functions (all deleted; only `_rename_one` stayed in `dtrpg-metadata-download.py`, still needed by `cmd_rename`). One `TagApp` instance handles a whole run — single file or `--root` batch alike, one code path instead of two. Orchestration is a single linear coroutine (`TagApp._run_flow`, run as a Textual worker) that `await self.push_screen_wait(...)`s through each file in turn, not a `Message`-passing state machine — a direct async translation of the old procedural `cmd_tag()`/`_tag_one()` control flow, chosen specifically because it made the port easy to verify against the original line by line. (`push_screen_wait()` — push a screen, `await` its `dismiss()` result — only works from inside a worker; that's why `_run_flow` is `@work`-decorated rather than called directly from `on_mount`.) Every blocking call (`DtrpgClient.search_library`/`get_product`/`enrich`, `write_metadata()`, `plan_rename()`/`apply_rename()` — all synchronous pikepdf/requests I/O) goes through `TagApp._call()`, a thin `asyncio.to_thread()` wrapper, so the UI doesn't freeze while one is in flight.

`ConfirmScreen` shows every field about to be written as an editable form (title, publisher, series, series index, description, tags, ISBN, product URL), pre-filled from the matched/overridden `ProductMetadata` — not just a read-only preview with an occasional series field, which is what it originally was. `TagApp.action_confirm()`'s edited values are rebuilt into a `ProductMetadata` by `apply_edits()` (a `dataclasses.replace()` over the original match, so `source`/`authors`/`product_id` survive untouched even if title/series/etc. are hand-edited — `product_id` in particular has to stay whatever was actually fetched, or `dc:identifier` and `--rename` would end up pointing at the wrong DriveThruRPG listing). A batch-wide default series (from `BatchSeriesModal`) is applied as this form's starting value via `resolve_series()`, same as before, but it's now just a pre-filled, still-editable `Input` rather than a field that's silently skipped — the user can override it per book without it ever being a secret what's about to be written.

`TagApp._maybe_ask_series()` runs right after `ConfirmScreen` closes, for every path that goes through it (candidate pick, manual override, manual entry): if the confirmed metadata's series is still blank at that point, a dedicated `SeriesModal` dialog asks once more -- "Series for {title}: / Leave blank for no series.", mirroring `BatchSeriesModal`'s own convention -- before writing. It's a final check, not a first ask: `ConfirmScreen` itself already starts pre-filled with any batch default or match-provided series and lets it be edited freely, so this only fires when it's genuinely still empty, catching an oversight rather than nagging on every write.

Outcome lines ("Wrote metadata to X", "Renamed: X -> Y", "Skipped.") are shown via `self.notify()` toasts, not a permanently-visible log widget — Textual's screen stack fully occludes whatever's beneath a pushed screen, so a naive port of the old always-visible printed lines would have fought the framework rather than used it. Every line is also appended to `TagApp.history` (plain list) so `tests/test_tag_tui.py` can assert on run outcomes without parsing rendered output. The app quits itself the instant a run (or a mid-batch `q`) finishes — no "press q to exit" screen — via `self.exit(message=summary)`; Textual prints that `message` to the real terminal itself, after the alternate screen buffer's already torn down, which is why the completion notice shows up as plain terminal output rather than one more TUI screen.

**Desktop GUI (`gui_app.py`/`gui_tag_flow.py`):** a PyQt6 app covering every subcommand in one window (Tag/Scan/Review/Write PDFs/Rename/All/Preferences), added on request as an alternative to the terminal entirely. Presentation layer only, exactly like `tag_tui.py` — every tab calls straight into `matcher.py`/`review.py`/`pdf_writer.py`/`renamer.py`, none of which know a GUI exists. `cmd_scan()`'s own inline matching loop was factored into `matcher.run_scan_batch()` (progress-callback-aware) specifically so the Scan tab and the CLI share one copy instead of two slowly drifting apart — the only change to existing business logic this feature required; `cmd_scan()`'s printed output is unchanged.

**This replaced an earlier Tkinter version of the same GUI, built first and then fully rewritten.** The trigger was an unresolved widget-rendering bug: a custom-bordered, scrollable Description field misaligned and never showed a focus ring on one real machine, despite the implementation being verified correct by every means short of running it there (property inspection, direct pixel-geometry measurement, a simulated real click) and despite a confirmed full process kill and relaunch. That bug was the latest in a run of subtle Tk/Tcl platform-rendering quirks this project kept hitting — Tk delegates widget painting to native OS APIs, which is exactly where each of these discrepancies traced back to. Qt paints its own widgets, so switching removes this whole class of bug by construction rather than working around one more instance of it. Both the API-key-leak and CSV-injection findings elsewhere in this doc, and the two Tk-specific bugs the *old* GUI's test suite caught (a `ttk.Treeview.identify_column()`/`.bbox()` disagreement about column boundaries, and a `RenameTab` dry-run-default bug below), were real and are preserved here since they're not toolkit-specific; the border/rendering saga itself, and the Tkinter-only architecture notes that went with it (a `queue.Queue`+`root.after()` polling loop, and a keybinding hazard around `Toplevel`-level letter mnemonics), are not carried forward in detail since neither has any Qt analog.

Every tab that can block (network calls, pikepdf I/O) runs its work on a background `QThread` via `UiTaskRunner`, whose log lines reach the log `QPlainTextEdit` through a queued Qt signal connection — Qt automatically marshals a signal emitted from a worker thread onto the thread its connected slot's receiver lives on, so there's no polling loop (unlike the old Tkinter version's `queue.Queue`+`root.after()` polling — a real simplification, not just a port). Only one job per tab runs at a time (the Run button disables itself while busy).

The Tag tab is the interesting case: the actual tagging work (network calls, pikepdf I/O) must run off the GUI thread so the window doesn't freeze, but only the GUI thread may build/exec a `QDialog`. `TagFlowController` (`gui_tag_flow.py`) is a plain, framework-agnostic class — an almost line-for-line port of `TagApp`'s own orchestration methods from `tag_tui.py`, reusing `tag_tui.py`'s pure helpers and result dataclasses directly (`resolve_series`/`build_manual_metadata`/`apply_edits`/`format_candidate_lines`/`do_rename`/`CandidateResult`/`ManualEntryResult`/`ConfirmResult`, none of it reimplemented) — that only needs a `notify(kind, payload, response_q)` callback and a `log(line)` callback, both supplied by `TagWorker` (a `QObject` living on a background `QThread`). Every `await push_screen_wait(...)` in the Textual original becomes a blocking `self._ask(kind, payload)`: it builds a fresh single-slot `queue.Queue`, calls `notify` (which just emits `TagWorker.dialog_requested`), and blocks *only the worker thread* on that queue's `.get()`. `TagTab`'s `_on_dialog_requested` slot — connected with Qt's default auto/queued cross-thread connection, so it always runs on the GUI thread regardless of which thread emitted the signal — builds the matching `QDialog` subclass and calls `.exec()` (Qt's own "block this thread until the modal window closes" primitive, playing the same role `Toplevel`+`wait_window()` played before), then puts the dialog's `.value` on the response queue, unblocking the worker. Unlike the Tkinter version, there's no separate pending-request backlog to drain on window-close: `.exec()` blocks the *entire* GUI event loop while a dialog is up, so the window can never be closing at the same moment a dialog request is unanswered.

Every checkbox in the GUI (BookOrbit mode, Convert images, Rename) has a short explanatory `_make_hint_label()` underneath it (`gui_app.py`, shared by `WritePdfsTab`/`AllTab` there and `TagTab` in `gui_tag_flow.py`, so the wording for a given flag can't drift between tabs), and the BookOrbit hint links to `https://bookorbit.app/` via `_make_link_label()` — a real `QLabel` with rich-text `<a href>` and `setOpenExternalLinks(True)`, unlike Tkinter's `ttk`, which has no hyperlink widget at all and had to fake one.

The Review tab is the scan → approve → write-pdfs workflow's approval step done entirely in-GUI instead of a spreadsheet handoff — `review.csv` loaded into one in-memory `list[ReviewRow]` (the single source of truth) shown in a `QTableWidget` (not `QTableView`+a model class — this project favors directness over architecture for architecture's sake, and `rows_by_filename` staying the single source of truth doesn't need one). `status` is editable via `StatusDelegate` (a `QStyledItemDelegate` whose `createEditor()` returns a closed-choice `QComboBox` locked to `Status`'s four values — free text here would silently break `ReviewRow.is_approved()`'s exact string match); `series`/`series_index` need no custom delegate at all, since `QStyledItemDelegate`'s own default editor for a plain editable cell is already a line edit. Everything else (publisher/authors/tags/product_url/isbn, and a multi-line field for description) is edited via a detail form below the grid, populated on row selection (`currentCellChanged`). Both surfaces write into the same in-memory rows so the grid and the form can't diverge. **`_populate_table()` must `table.blockSignals(True)` around programmatic population** — `QTableWidget.itemChanged` fires for `setItem()` during bulk insert just as it does for a real user edit, with no Tkinter analog (`ttk.Treeview` has no equivalent signal); omitting this would fire a spurious commit into `rows_by_filename` for every cell of every row on every reload, guarded by a dedicated test (`tests/test_gui_app.py`'s `test_review_tab_no_save_during_population`).

**Even under Qt, the Description field (`QPlainTextEdit`) had a black border with no blue focus ring while every `QLineEdit` field around it had a grey border that turned blue on focus — the exact same visible symptom as the Tkinter bug that triggered this migration, for the exact same underlying reason.** `QLineEdit` gets a native-looking grey border (blue on focus) for free from Qt's macOS style, since qmacstyle draws it the way a real `NSTextField` would; `QPlainTextEdit`/`QTextEdit` don't get that same native treatment — their frame is just a generic `QFrame` panel with no focus-color change, since Qt has no equivalent native-control mapping for a multi-line text view. This took four real, independently-verified fixes to actually resolve — each one initially looked complete by reasoning about what Qt "should" do, and each was wrong until checked against an actual screenshot (`QWidget.grab()`, saved to a file and read back), which is why this is recorded in this much detail: **reasoning about Qt's stylesheet/focus system is not a substitute for looking at a real rendered pixmap.** All four fixes now live in one place, `_StyledTextEdit(QPlainTextEdit)` in `gui_app.py`, used everywhere a multi-line field is needed (`_make_log_widget()`, the Review tab's `_DescriptionEdit`, and both Tag-flow dialogs' description fields in `gui_tag_flow.py`) instead of a bare `QPlainTextEdit`:
1. **No border/focus styling at all initially** — fixed by adding a QSS rule (`_TEXT_EDIT_STYLE`): `QPlainTextEdit { border: 1px solid ...; } QPlainTextEdit:focus { border: 1px solid ...; }`. Unlike Tkinter (no declarative focus-state styling at all, requiring manual `FocusIn`/`FocusOut` bindings and a forced repaint), Qt's QSS supports `:focus` natively — in principle, one rule should have been enough.
2. **Applying that stylesheet via `QApplication.setStyleSheet()` (app-wide) fixed the Description field but silently killed the native blue focus ring on every `QLineEdit` in the app too** — caught from a real screenshot showing every field's focus ring gone, not just the untargeted ones. Setting *any* stylesheet on the `QApplication`, even one whose only selector is `QPlainTextEdit`, makes Qt route *all* widget painting through its `QStyleSheetStyle` proxy instead of the native macOS style, which suppresses native chrome (the focus glow) even for widgets the stylesheet doesn't target. Fixed by applying the stylesheet per-widget instead (in `_StyledTextEdit.__init__`) — a stylesheet set directly on one widget only affects that widget and its children, leaving sibling `QLineEdit`s on native rendering untouched.
3. **Still incomplete: rounded grey corners, but the four straight edges were still black** (a second real screenshot). `QPlainTextEdit` is a `QAbstractScrollArea`, which paints its own native `QFrame` panel independently of the QSS `border` property — the QSS border was being drawn, but the native sunken-panel frame was still painted too, visible wherever the square native frame didn't coincide with the QSS's rounded corners. Fixed by also calling `setFrameShape(QFrame.Shape.NoFrame)` before applying the stylesheet, removing the native frame layer entirely.
4. **Still not fixed after both of the above — "exactly the same."** This time verified with pixel-level precision rather than eyeballing: cropped a real screenshot and sampled the actual rendered border color of a genuine `QLineEdit` (`(235, 235, 235)` / `#ebebeb`) versus the guessed `_TEXT_BORDER_COLOR` that had been in use since the Tkinter version (`#a3a3a3` / `(163, 163, 163)`) — nearly 3x darker, which reads as "black" sitting next to a real `#ebebeb` border. Fixed by matching the measured value exactly instead of eyeballing a "plausible-looking grey."
5. **Separately, the `:focus` border still never rendered on a real focus change even with fixes 1-4 in place, despite `hasFocus()` correctly reporting `True`.** `QAbstractScrollArea` delivers keyboard focus through its internal `viewport()` child widget, not the outer widget the stylesheet targets, so the outer `QPlainTextEdit` never received its own `focusInEvent()`-triggered repaint the way a plain widget like `QLineEdit` would (confirmed by manually forcing `style().unpolish()`/`.polish()`/`.update()` after `setFocus()` and watching the blue border finally appear in an otherwise-identical screenshot). Fixed by overriding `focusInEvent`/`focusOutEvent` on `_StyledTextEdit` to do exactly that automatically on every focus change.
6. **Once colors/borders finally matched, the *focused* border still looked visibly thinner than native's, with corners that looked cut off rather than rounded — a real, if purely cosmetic, difference confirmed by comparing zoomed-in crops of both.** First tried nudging `_TEXT_EDIT_STYLE`'s focus state from `1px solid` to `2px solid` with a slightly bigger border-radius — a small improvement, but the user correctly called this "exactly the same" in substance: a flat QSS border, at any width, is still a crisp uniform line, and the real native ring (confirmed by pixel-sampling a real focused `QLineEdit`) is a soft ~3px pale band *outside* the control's own thin border, not a thicker/bluer version of that border. Asked the user how far to chase this (a solid border is "good enough" vs. a true custom-painted glow); they chose the glow.
7. **First glow attempt (`QGraphicsDropShadowEffect`, Qt's stock box-shadow-equivalent) was compared directly against a real screenshot, side by side, and was visibly wrong in its own way: darker and thinner near the edge, fading out fast, reading as a "shadow" rather than the native ring's fairly uniform pale band.** A Gaussian blur's density is inherently highest right at the source edge and falls off with distance — no combination of blur radius/opacity produces the flatter, more even-width band the real ring has. Replaced with `_FocusRingEffect`, a custom `QGraphicsEffect` subclass whose `draw()` paints an actual rounded-rectangle ring with `QPainter` (a fixed-width translucent stroke offset outward from the widget's own bounds) instead of approximating the shape through a blur algorithm — `boundingRectFor()` is what lets Qt reserve room to paint outside the widget's normal geometry, which a plain `paintEvent` override can't do.
8. **That first custom-ring version was itself wrong in two more ways, both reported directly from real screenshots (not caught by any self-review beforehand): a visible white gap between the ring and the field's actual border that native doesn't have, and corners distinctly rounder than native's own.** `RING_MARGIN` (the offset between the widget's own border and the ring) had been set to `2.0` on the assumption of a small breathing gap; a real screenshot showed native's ring sits flush against the control with no gap at all. `RING_RADIUS` had been set to `8.0`, visibly rounder next to a real native field's much more rectangular, barely-rounded corners. Fixed by setting `RING_MARGIN = 0.0` (flush) and `RING_RADIUS = 6.0` (closer to the ~5px native radius measured earlier), re-verified with a fresh side-by-side screenshot crop before calling it done.

**`RenameTab`'s "Dry run (preview only)" checkbox defaulted to checked — a real bug, reported by the user as "I checked off rename and it did not rename the file" the first time they used it (an application-logic bug, not toolkit-specific — it survived the Tk→Qt rewrite as a fact to preserve, not fix again).** The CLI's own `--dry-run` flag is `action="store_true"` (off unless passed — `rename` really renames by default), but the GUI checkbox inverted that: clicking "Run Rename" without noticing and unchecking the box first silently only logged "Would rename: ..." and touched nothing, the opposite of what running the tab's primary button should do by default. Fixed by defaulting the checkbox to unchecked, matching the CLI. Verified against the real widget (not just the underlying function): filled in a path, left the checkbox untouched, clicked Run — file and sidecar actually renamed on disk. The Tag tab's own "Rename after write (--rename)" checkbox was never affected by this — it defaults to unchecked, matching `--rename`'s own `action="store_true"`, and correctly renames when checked.

`gui`'s PyQt6 dependency is an ordinary PEP 723/`uv`/pip dependency, unlike Tkinter's Tk bindings (a system-level Python build feature no dependency manager controlled) — under `uv run --script` (the primary supported path), `uv` resolves and installs it automatically, same as every other dependency here, with no OS-specific install step. `cmd_gui()` still lazily imports `PyQt6`/`gui_app` inside the function body rather than at module level, so a missing GUI dependency only affects `gui`, not every other subcommand — but the guard itself is now a short one-shot `ModuleNotFoundError` check (covering the `requirements.txt`+venv path, where forgetting `pip install -r requirements.txt` is a plausible mistake), not the old multi-branch `brew`/`apt` guidance, since there's no OS package to walk anyone through installing anymore.

**Preferences (`preferences.py`/`preferences_tui.py`):** a saved API key and DriveThruRPG account name, reachable from both UIs (the `preferences` TUI subcommand and the GUI's Preferences tab) as well as directly editing `data/preferences.yaml`. **This is a deliberate, explicit change to this project's previous policy that the API key only ever comes from `DTRPG_API_KEY`** — added on request, not found as a gap. Saving one here means it now also lives in a plaintext file on disk, not only in an environment variable; `save_preferences()` sets owner-only file permissions (`0600` via `os.chmod`, best-effort — not every platform/filesystem honors it) and the path is gitignored (`data/preferences.yaml`), but neither of those makes it as protected as an environment variable that only ever existed in one shell session. `resolve_api_key()` has an existing `DTRPG_API_KEY` win over the saved file every time (verified: setting both and calling `build_client()` returns the environment variable's value, not the file's) specifically so saving a preference can't silently change behavior for anyone already relying on the environment variable — the file only matters as a fallback when no environment variable is set. `config.yaml` gained a `preferences:` key (default `data/preferences.yaml`) purely as an overridable *path*, the same pattern as `manual_overrides`/`review_csv` — the actual secret never goes in `config.yaml` itself, which is still meant to be safe to share/commit. The `dtrpg_name` field is currently just stored and shown back in both UIs — not read by any matching/API logic yet (added for planned future use, per the user's own request, not because something today needs it) — so don't assume it's wired into `DtrpgClient` anywhere; check before relying on it if that changes.

**`Preferences` also grew the three sibling-script paths** (`gurps_hyperlink_script`/`mongoose_hyperlink_script`/`grayscale_script`), settable in both UIs (the GUI's Preferences tab gets three `QLineEdit`+Browse-button rows, filtered to `*.py`; the TUI gets three more `Input` fields) instead of only being editable by hand in `config.yaml`'s placeholder keys. `resolve_path(preference_value, config_value, default)` in `preferences.py` is the shared three-source resolver (`dtrpg-metadata-download.py`'s `_resolve_script_paths()` and `gui_app.py`'s `resolve_script_paths()` are thin wrappers over it, one per presentation layer, both calling `load_preferences()` then `resolve_path()` for each of the three) — **deliberately the opposite precedence from `resolve_api_key()`**: the saved preference wins over `config.yaml`, not the other way around. This isn't an inconsistency, it's a different situation: `DTRPG_API_KEY` predates the Preferences feature by a long time, so protecting existing users of the environment variable from a silent behavior change mattered; these three keys were only ever added to `config.yaml` as a stopgap in the same work that built the features using them, so there's no pre-existing workflow a saved preference could surprise, and the Preferences tab is meant to be the primary way to set them going forward. Verified directly: saving a script path via `PreferencesTab._save()`, reloading a fresh tab instance, and calling `resolve_script_paths()` with a *different* value also present in `config.yaml` all confirm the saved preference is what actually gets used.

**Logging vs. the alternate screen buffer.** Textual takes over the terminal via an alternate screen; a plain `logging.StreamHandler` writing a `logger.warning()`/`logger.exception()` (already present in `matcher.py`/`dtrpg_client.py`) straight to stderr mid-run would corrupt the display. `main()` now configures `logging.basicConfig(handlers=[TextualHandler()])` (from `textual.logging`) instead of the default handler — confirmed from `TextualHandler`'s own source that it checks `active_app.get()` and routes to the running app's own log instead of stderr whenever one is active, falling back to plain stderr when none is (so this is a safe universal replacement, not a `tag`-specific special case; every other subcommand's logging is unaffected). This particular fix was verified by reading `TextualHandler`'s source and confirming `main()`'s `basicConfig` call happens before `TagApp.run()` by construction, not by capturing a real terminal's rendered output — an actual live-terminal check (does a warning firing mid-run visually corrupt anything) is still open; see the TUI rewrite's own notes for what was and wasn't verified this way.

**DriveThruRPG API is undocumented — treat field-path assumptions as provisional.** `dtrpg_client.py`'s docstring records what's actually confirmed vs. inherited from third-party reverse-engineering:
- `order_products` (purchased library, via `search_library`) and the `auth_key`/token auth flow were reverse-engineered from `glujan/drpg`'s source and are trusted.
- **`auth_key` requires the application key as a URL query param (`?applicationKey=...`), which means `resp.url` for that call literally contains the key — a real leak surface, not just a theoretical one.** Two paths let it out: a failed JSON parse or missing `token` field used to dump the raw `resp.url` (key included) to a plaintext file in `data/debug/`, and any non-401 HTTP error let `requests.HTTPError`'s default message (which embeds the URL) propagate uncaught to the terminal/traceback — exactly what someone would paste into a bug report while asking for help. Fixed in `_authenticate()`/`_dump_debug()`: the debug-dump path now redacts the key wherever it appears in a URL (not just at this one call site, so any future endpoint that also leaks a secret into its URL is covered), and the `raise_for_status()` failure re-raises a sanitized `DtrpgApiError` with `from None` specifically so the key-bearing original exception is never chained into anything that gets printed. Found via a security audit ahead of making this repo public, not by request.
- `products/{id}` (product detail — authors, publisher, description, tags) was *initially* modeled on `quickwick/drivethrurpg-calibre-plugin`, which assumes a JSON:API envelope (`{"data": {"attributes": ...}}`). That assumption was wrong against a real authenticated account — the live response is a **flat** object. `_parse_product_detail` is now written against the confirmed flat shape (verified from an actual `data/debug/` dump), not the plugin's code. If matching breaks again with a `KeyError` during product-detail parsing, check `data/debug/` for the raw dump before changing the parser blind.
- There's no structured "series"/series-index field anywhere in the API; series info lives inside the title text itself, so `ProductMetadata.series` is expected to come from matching/manual overrides, not the client.

**Library matches are cheap but thin; catalog matches are rich but rate-limited.** `search_library()` only has title+publisher (that's all `order_products` carries) and does its matching *locally* against a cached full-library pull — no server-side query. `search_catalog()` hits the real search endpoint and enriches every result via a `products/{id}` call immediately (already rate-limited, only ~6 results). Because of this asymmetry, a library-sourced match that's missing a description (or isbn/authors/tags) doesn't mean DriveThruRPG has none — it means nobody's called `DtrpgClient.enrich()` on it yet. `enrich()` is deliberately *not* called on every candidate `search_library()`/`find_candidates()` returns (that would burn the rate limit on options nobody picks); it's called once, lazily, on whichever candidate is actually kept — see the call sites in `matcher.match_file()`/`_maybe_enrich()` and `dtrpg-metadata-download.py`'s `_tag_one()`.

**A library entry's `productId` can go stale.** DriveThruRPG can re-list a purchased title under a new product ID after purchase (confirmed against a real purchase: "Delta Green: Handler's Guide" 403'd — `403.02`, "You cannot access this content right now" — on the ID from the user's `order_products` entry, while the current listing at a different ID fetched cleanly). `DtrpgClient.enrich()` handles this itself: on a failed direct fetch, `_enrich_fallback_by_title()` retries via `search_catalog(meta.title)` and, if found, also overwrites `meta.product_id` with the corrected one — necessary so the *right* ID ends up in the file's `dc:identifier`, not the dead one. No caller-side changes needed; this is transparent to `matcher.py` and the CLI.

**Image conversion (`image_converter.py`):** ported from a separate personal project (`mac-pdf-rgb-fix`) that fixes CMYK/JPEG2000 images in PDFs for Apple's PDF renderer — ported, not merely called out to, since the two projects don't share a runtime; `convert_images_to_rgb(path)` re-encodes every CMYK/grayscale/JPX image XObject in a PDF to RGB JPEG (Indexed/palette images stay lossless FlateDecode) and saves in place. Uses PyMuPDF (`fitz`) for color-managed CMYK→RGB conversion — Pillow's own CMYK→RGB produces a green cast — and Pillow for JPEG encoding; this project's first new dependency since `textual`, and a genuinely different PDF library from `pikepdf`, which the rest of this project uses. All of the source project's hard-won constraints were ported verbatim, not re-derived: CMYK images without an embedded profile get re-tagged with a real CMYK ICC profile before conversion (macOS's `Generic CMYK Profile.icc`; falls back cleanly elsewhere), output RGB images get an explicit sRGB ICC profile rather than bare `/DeviceRGB` (embedded both at the PDF colorspace level and inside the JPEG stream itself, since some decoders trust the JPEG's own profile over the PDF wrapper's), `/Mask` vs `/SMask` is preserved by checking the original object's key rather than assuming, shared image XObjects are processed once by xref not once per page, and `deflate_images` is never enabled on save (would silently undo the JPEG encoding).

**Runs before pikepdf ever opens the file for metadata writing, never after — this ordering is deliberate, not incidental.** `write_metadata()` calls `convert_images_to_rgb()` (when `--convert-images`/`convert_images=True`) immediately after the one-time backup, *before* its own `pikepdf.open(...)` block. PyMuPDF's `doc.save()` is a different library's save path than pikepdf's, and pikepdf's Calibre-specific XMP writing (`_set_calibre_series()` etc.) reaches into private internals to produce a structure real Calibre requires but that "looks right" through any generic reader including PyMuPDF's own metadata APIs — letting PyMuPDF's save happen *after* that write would risk exactly the looks-fine-but-silently-breaks failure mode the series bug above already burned real time on, just from a second library instead of a first attempt at the same one. Doing image conversion first means pikepdf's metadata write is always the last thing to touch the file. Verified concretely, not just reasoned through: built a real PDF with an embedded CMYK JPEG, ran it through `write_metadata(..., convert_images=True)` with a series/index set, and confirmed with real `ebook-meta` (not pikepdf reading its own write) that `Series: Sword Worlds #2` still comes through correctly afterward — the exact structure this ordering exists to protect. Also verified: a JPEG2000 image's pixel values survive the JPX→RGB→JPEG round-trip exactly (a solid test color in, the identical value out), and a converted page still renders via `page.get_pixmap()` rather than coming back blank/corrupted.

**A `--convert-images` failure is logged and swallowed, not raised — the write still proceeds with metadata-only.** Matches this function's existing sidecar-failure convention (losing one piece must not fail a write that could otherwise succeed) rather than the alternative of aborting the whole write over an image-conversion problem.

**Image conversion is a heavier, riskier operation than metadata writing, so no dedicated committed test was added for it** — this project's convention is ad hoc verification scripts for pikepdf/PDF-writing logic generally (`pdf_writer.py` itself has none either, despite its own fragile Calibre-series history), with committed tests reserved specifically for UI screen/message-wiring risk (`tests/test_tag_tui.py`, `tests/test_gui_app.py`). The verification described above (a constructed CMYK+JPX PDF, real `ebook-meta` check, real page render) is the ad hoc equivalent for this module; re-run something like it if `image_converter.py`'s core loop ever changes.

**PDF hyperlinking (`rpg_hyperlink.py`), `--hyperlink-gurps`/`--hyperlink-mongoose` on `tag`/`write-pdfs`:** unlike everything else in this file, this is a deliberately *machine-specific* integration, not a general feature — it wraps completely separate sibling scripts (`hyperlink_pdf_universal.py` for GURPS, `hyperlink_pdf_mongoose.py` for Mongoose Publishing's Traveller line, both from the `gurps_4e_revised_hyperlink` repo that happens to live next to this repo on this particular machine) that auto-hyperlink in-text page/chapter references (`"see p. 208"` → a real clickable link), each tuned for one publisher's own reference conventions (see that repo's own extensive `CLAUDE.md`, which documents the Mongoose script as "a fork of `hyperlink_pdf_universal.py`'s logic, not a from-scratch rewrite"). One generic function handles both: `run_hyperlink_script(path, script_path, log=None)` loads whichever sibling script's `hyperlink_pdf(in_path, out_path)` function via `importlib.util.spec_from_file_location` (an absolute-path import, not `pip install`/vendoring — these are independent, independently-versioned scripts, not packages this project depends on) and calls it, since that function can't write in place (`shutil.copyfile` inside it raises `SameFileError` on a same-path copy) — same temp-file-then-`os.replace()` pattern as `convert_images_to_rgb()`, for the same reason (a failure partway through leaves the original untouched). The sibling script's own `<stem>_link_report.csv` (every link added/skipped, and why) is kept, renamed to match the final path. This file used to be `gurps_hyperlink.py` (`hyperlink_gurps_pdf()`) before the Mongoose script was added — confirmed the two sibling scripts share an identical function signature and return shape before generalizing, rather than assuming.

`gurps_hyperlink_script`/`mongoose_hyperlink_script`'s paths come from the saved Preferences file or `config.yaml` (placeholders there, matching `root`'s own placeholder convention — a real absolute path pointing into a specific person's home directory has no business being committed to a repo meant to go public; see "Preferences" below for the resolution order between the two) — a missing/misconfigured path produces a clean `HyperlinkResult(success=False, message=...)`, not a crash, so this degrades to a no-op-with-a-clear-log-line on any machine that doesn't have the sibling project, exactly like `image_converter.py`'s own failure handling. Both run in the same pre-pikepdf-open stage as `--convert-images` (after it, before `pikepdf.open()`), for the same "pikepdf's metadata write must be the last thing to touch the file" reasoning — verified concretely, not assumed, that this ordering is actually safe: built a synthetic PDF, added a real link annotation via PyMuPDF's `insert_link()`+`saveIncr()` (the exact mechanism both sibling scripts use), then ran it through the same `pikepdf.open(..., allow_overwriting_input=True)` → `pdf.save(path)` sequence `write_metadata()` uses for its own metadata write, and confirmed the link annotation survives intact on the other side (`fitz.open(...).load_page(0).get_links()` — present, correct target page, unchanged). `write_metadata()` runs `--hyperlink-gurps` and `--hyperlink-mongoose` independently of each other (`_run_hyperlink_step()`, called once per flag that's set) — mutually harmless if both were ever on at once, though in practice a given book is only ever one publisher's. The GUI checkboxes for both exist only on the Tag and Write PDFs tabs (not All), by explicit request — the CLI flags themselves are still present on all three (`tag`/`write-pdfs`/`all`) subparsers purely because `cmd_all()` shares `cmd_write_pdfs()`'s own `args` namespace and would otherwise raise `AttributeError` reaching for `args.hyperlink_gurps`/`args.hyperlink_mongoose` on an `all`-only run.

**Grayscale conversion (`rpg_grayscale.py`), `--convert-grayscale` on `write-pdfs`/`all`/`tag`:** a third sibling-script integration, same machine-specific-integration reasoning as `rpg_hyperlink.py` above, wrapping `convert_pdf_to_grayscale.py` from the same `gurps_4e_revised_hyperlink` repo. Genuinely different from the hyperlink scripts in one real way: it shells out to the actual Ghostscript binary (`gs`) via `subprocess`, a system package (`brew install ghostscript` on macOS) that PEP 723/uv/pip can't provide, unlike `pymupdf` (already a dependency here). A missing `gs` raises `FileNotFoundError` from inside the sibling script's own `run_ghostscript()`, caught specifically in `convert_pdf_grayscale()` for a clean, actionable message rather than a raw traceback. Bypasses the sibling script's own interactive `main()` prompting (whether to keep the front/back cover in full color) entirely, calling its two non-interactive functions directly — `run_ghostscript(src, dst)` then `restore_metadata_and_labels(original, converted, final, keep_producer, keep_color_pages)` — with `keep_color_pages` always empty (convert everything, covers included, matching that prompt's own default when accepted with Enter), since there's no interactive terminal to ask a per-file question through a batch write or a GUI checkbox. Needs two temp files, not one (`run_ghostscript()`'s own output can't be the same path it read from; `restore_metadata_and_labels()` separately needs its own `final` path distinct from both, since it holds `original` open via pikepdf while writing `final`) — same atomic-swap-only-on-success pattern as everywhere else in this family. Verified directly, not assumed, that running this *before* the hyperlink steps is safe: a link annotation added via PyMuPDF's `insert_link()`+`saveIncr()` survives Ghostscript's grayscale pass intact (confirmed by reading the link back with `fitz.get_links()`) — the sibling script's own `run_ghostscript()` already passes `-dPreserveAnnots=true`/`-c "/PreserveAnnotTypes [/Link] def"` for exactly this reason, but that claim was checked against a real link rather than trusted from the flag names alone. Also verified end-to-end that a Ghostscript-produced grayscale PDF survives a subsequent pikepdf metadata write (title/publisher both correct afterward), the same class of check every other step in this write pipeline has been held to.

`--convert-images` and `--convert-grayscale` are opposite operations on the same images, so they're mutually exclusive by explicit request — enforced at both layers, not just one: the CLI declares them via `argparse`'s `add_mutually_exclusive_group()` on each of the three subparsers that have them (`write-pdfs`/`all`/`tag` — a separate group instance per subparser, `argparse` groups don't span parsers), and the GUI's `_make_mutually_exclusive(a, b)` helper wires each pair of checkboxes so checking one un-checks the other via `toggled` signals (only fires on an actual state change, so no infinite signal loop) — used on all three tabs that carry both checkboxes (Tag, Write PDFs, All). `write_metadata()`/`write_approved()` themselves don't enforce this — they just run whichever step(s) they're told to — since the constraint belongs at the interfaces a human or script actually drives, not duplicated into the business-logic layer underneath both of them.

**Background-layer tagging (`rpg_background_layer.py`), `--background-layer`/`--remove-background` on `write-pdfs`/`all`/`tag`:** a fourth sibling-script integration, same machine-specific-integration reasoning as `rpg_hyperlink.py`/`rpg_grayscale.py` above, wrapping `castles_and_crusades_background_layer.py` from the same `gurps_4e_revised_hyperlink` repo. Tags each page's full-page decorative background as a toggleable Optional Content Group (OCG) layer, or deletes it outright. Genuinely different from all three prior integrations in its invocation mechanism: this sibling script has no separable non-interactive library function to import (unlike `hyperlink_pdf()` or `run_ghostscript()`/`restore_metadata_and_labels()`) — its whole logic lives inside a single `argparse`-driven `main()`. Rather than duplicate that orchestration here, `apply_background_layer(path, script_path, remove=False, log=None)` invokes it as a real `subprocess` via `sys.executable src dst [--remove]`, exactly the way its own author runs it from a terminal. Same temp-file-then-`os.replace()` atomic-swap pattern as the rest of this family (the sibling script's own `pikepdf.open()` call has no `allow_overwriting_input=True`, so it can't write back over what it read even if asked to), and never raises — a missing script path or a non-zero exit both come back as `BackgroundLayerResult(success=False, message=...)`, logged and swallowed by `write_metadata()` exactly like every other optional pre-write step in this project.

Runs *first* among the optional pre-pikepdf steps (before `--convert-images`/`--convert-grayscale`/hyperlinking) — if the background is about to be removed entirely, there's no reason for a later image-conversion pass to waste time re-encoding it first, and OCG tagging only ever touches an XObject's `/OC` key, completely disjoint from the image-encoding keys or `/Annots` links the other steps touch. Verified directly, not just reasoned through: built a synthetic PDF with a `/Bg` image XObject wrapped in `q...Q` (the sibling script's `find_removal_span()` requires an enclosing bracket to identify a removable span — a real script constraint, confirmed when a first test PDF without the wrapping reported "skipped 1 pages" instead of actually removing anything), ran both tag mode and `--remove` mode through the wrapper, and confirmed with real `ebook-meta` that a subsequent pikepdf metadata write still comes through correctly afterward (`/OCProperties` present, `/OC` set on the Bg XObject in tag mode; the image gone entirely in remove mode) — the same "must survive the final metadata write" bar every other pre-write step in this pipeline is held to.

`background_layer_script`'s path comes from the saved Preferences file or `config.yaml` (same resolution order as the other three sibling-script paths — see "Preferences" above), and `--background-layer`/`--remove-background` are mutually exclusive by construction (opposite operations on the same background), enforced the same way as `--convert-images`/`--convert-grayscale`: a dedicated `argparse` mutually-exclusive group per subparser, and `_make_mutually_exclusive()` wiring the two checkboxes on the GUI's Tag and Write PDFs tabs (not All — same "machine/publisher-specific, not a general feature" reasoning that keeps `--hyperlink-gurps`/`--hyperlink-mongoose` off the All tab's UI too, even though the CLI flags themselves exist on all three subparsers since `cmd_all()` shares `cmd_write_pdfs()`'s own `args` namespace).

**Embedded PDF metadata targets Calibre's own format, verified against a real installed Calibre 9.13 — not guessed, and not just "round-trips through pikepdf" (see the series bug below for why that distinction matters).**
- `dc:creator`/`dc:publisher` both get the **publisher** name, not DriveThruRPG's actual author list — deliberate policy (DTRPG's per-book author credits are too inconsistent to trust for this library), carried through every metadata-target change this project has been through (Kavita → BookOrbit-only → current Calibre+sidecars) and re-confirmed each time rather than silently dropped.
- `dc:description` → Comments, `dc:subject` → Tags, both filtered through `TAG_BLOCKLIST` in `dtrpg_client.py` for the latter.
- `pdf_writer._set_calibre_identifiers()` writes `xmp:Identifier` (dtrpg + isbn) via pikepdf's private XMP internals (`_xmp_doc`, `_get_rdf_root`) — there's no supported public-API way to write a qualified/structured XMP property (`rdf:parseType="Resource"`), and Calibre's own reader (`calibre/ebooks/metadata/xmp.py`) requires exactly that shape. Guarded by `except AttributeError` in case pikepdf's internals change.
- **`pdf_writer._set_calibre_series()` exists for the same structural reason, and its absence was a real, previously-undiscovered bug**: an earlier version wrote `calibre:series`/`calibre:series_index` as plain scalar XMP properties via pikepdf's public dict API. That round-trips through pikepdf perfectly (readable via `pikepdf.open(...).open_metadata().get(...)`) and was believed correct for most of this project's history — but real Calibre's reader (`read_series` in `xmp.py`) never actually recognized it: `calibre:series` must wrap its value in a nested `rdf:value`, and the index is a *differently-namespaced* child (`calibreSI:series_index`, URI `http://calibre-ebook.com/xmp-namespace-series-index`) nested inside the series element, not a sibling `calibre:series_index` property. Caught by testing against `ebook-meta --to-opf` on a real, never-before-touched file — a plain scalar write silently produces no "Series" line; watch for this failure mode (looks-fine-in-pikepdf, invisible-in-the-real-app) if any other Calibre-specific field is added later. `series_index` is only written when actually known (empty/non-numeric `row.series_index` omits the `calibreSI:series_index` element rather than defaulting to `1.00`) — verified this doesn't change what Calibre *displays* (its own `read_series()` also defaults a missing index to 1.0), it just avoids fabricating a false "confirmed #1" in the raw data, and keeps this consistent with the sidecars, which were already correctly omitting it in this case.
- ISBN validity is checked before writing (`sidecar_writer._split_isbn()`, imported into `pdf_writer.py` for this) — a `row.isbn` that isn't 10 or 13 digits gets skipped with a warning rather than written unconditionally under a scheme readers will trust as a real ISBN. This check existed in the BookOrbit-only era (`_isbn_field()`) and was accidentally dropped in the revert to Calibre format; restored via code review, not by request.
- `_get_or_create_rdfdesc()` is shared by both private-internals writers — reuses the one `rdf:Description[@rdf:about=""]` block pikepdf's own public API writes into, rather than creating a second one (RDF treats multiple Description blocks with the same subject as equivalent, and Calibre's own reader XPaths are `//`-rooted so block placement doesn't matter to it either — this is purely for tidier output).
- `pdf:Keywords` also gets the tags list (joined with `"; "`) — pikepdf's docinfo sync maps the classic `/Keywords` Info-dict field from `pdf:Keywords` specifically, not from `dc:subject`, so a reader that only looks at the Info dictionary would otherwise see it empty. Docinfo sync separately maps `/Subject` from `dc:description`, not from `dc:subject` — a real "Subject" vs. "Tags" naming confusion worked through earlier in this project; don't conflate the two.
- **Because this targets Calibre's actual XMP convention rather than something invented for this project, any reader that implements Calibre-compatible XMP parsing picks it up too — confirmed for Kavita, not just Calibre itself.** `Kavita.Services/Helpers/PdfMetadataExtractor.cs` in Kavita's real open-source repo (`Kareadita/Kavita`) explicitly registers the same `calibre`/`calibreSI` XMP namespaces and reads `//calibre:series/rdf:value` and `//calibreSI:series_index` — the exact nested structure `_set_calibre_series()` writes — plus standard `dc:title`/`dc:creator`/`dc:publisher`/`dc:description`/`dc:subject`. This is wired into Kavita's real scan path (`ReadingItemService.ParseFile()` → `BookService.GetComicInfo()` → `PdfComicInfoExtractor` → this extractor, gated only by a normal per-library "enable metadata" setting), not a dead/unreachable path like the BookOrbit `.opf` precedence trap above. **One real, confirmed gap: ISBN.** Kavita's PDF extractor looks for `pdfx:isbn` or `prism:isbn`, neither of which this project writes — ISBN here lives inside Calibre's own qualified `xmp:Identifier` Bag (see `_set_calibre_identifiers()` above) instead, which Kavita's PDF path never reads. So title/publisher/author/description/tags/series/series-index all carry over to Kavita; ISBN currently does not.
- **One deliberate exception to "Calibre format only": `bookorbit:seriesName`/`bookorbit:seriesIndex` also get written**, in BookOrbit's own simple scalar form (no nested-value structure needed there — confirmed from BookOrbit's real `pdf-xmp-reader.ts`). This isn't redundant with the `.opf` sidecar — see the sidecar section below for why the sidecar's series data turned out to be unreachable in practice, which is what forced this. If "embedded PDF is pure Calibre format" ever gets revisited, this is the one field that has a real, verified reason to be the exception.
- **Re-tagging a file must clear stale series data, not just add new data** — a third real bug, caught by code review right after the previous two. `write_metadata()` edits a PDF's *existing* persisted XMP tree in place (unlike `sidecar_writer.py`, which fully regenerates its output each run and so has no staleness exposure at all). The series-writing block only ran `if row.series:` — meaning re-tagging a file to a match with *no* series left all four series-related properties (`calibre:series` and its nested index, plus both `bookorbit:` fields) silently in place from whatever the previous match had. Fixed: an explicit `else` branch clears all four when the current match has none, and `bookorbit:seriesIndex` is explicitly deleted (not just left unset) whenever the current match has a series but no numeric index. Verified against both real `ebook-meta` and BookOrbit's real XMP reader across a full write → retag-different-index → retag-no-series sequence, not just a single write.

**Sidecar files (`sidecar_writer.py`) target BookOrbit's and Grimmory's own real formats, each verified against that app's actual open-source parser/writer — not guessed:**
- BookOrbit `.opf`: verified end-to-end by running BookOrbit's real TypeScript `opf-parser.ts` (via `tsx`, with `pdf-lib`/`fast-xml-parser` installed) against a file this project wrote. Standard EPUB2/Calibre-style OPF; series via the same `<meta name="calibre:series">` convention Calibre itself uses (a *different*, much simpler mechanism than the PDF-embedded case above — plain `name`/`content` attributes on OPF, no namespaced element/nested-value structure needed); ISBN auto-bucketed into isbn10/13 on BookOrbit's end from one `<dc:identifier opf:scheme="ISBN">`, so no bucketing needed on the write side.
- **The `.opf` sidecar's series data is real but unreachable by BookOrbit in practice, given how its scanner actually works — this was a second real bug, caught only after a user reported BookOrbit not importing series despite everything above testing correct in isolation.** BookOrbit's default `metadataPrecedence` for PDFs is `['embedded', 'opfFile']` (confirmed from `scanner.constants`/`library.constants.ts`: `LIBRARY_METADATA_PRECEDENCE_DEFAULT` filtered down to the two sources `SCANNER_METADATA_SOURCES` supports for PDFs), and `extractFirstAvailableMetadataSource()` in `scanner.service.ts` stops at the *first* source that extracts *anything* — it's a whole-source fallback, not a per-field merge:
  ```ts
  for (const source of sources) {
    const extracted = await this.extractMetadataSource(...);
    if (extracted) return;   // never reaches opfFile if embedded returned anything
  }
  ```
  Since a Calibre-tagged PDF always has *some* embedded metadata, `embedded` always "wins" and `opfFile` is never even opened — regardless of what's actually in it. This is why `bookorbit:seriesName`/`seriesIndex` are also written directly into the embedded PDF (see above); don't assume the `.opf` is actually being read for series, or trust "the sidecar parses correctly in isolation" as proof a *scanned* BookOrbit library will show the data — verify end-to-end against the precedence logic too.
  **By default the `.opf` is no longer written at all** — pointless when the embedded PDF always wins, per the above — unless `--bookorbit-mode` is passed. That flag flips the strategy entirely instead of fighting the precedence: rather than duplicating series into the embedded PDF, `write_metadata()` strips **all** PDF-level metadata (the full XMP packet *and* the classic Info dictionary — not just this tool's own fields, since a leftover publisher-set `/Title` alone is enough for BookOrbit's "first source that returns anything" check to short-circuit past the sidecar) and writes the `.opf` in that mode instead. Off by default; the Grimmory `.metadata.json` sidecar is written unconditionally either way and is untouched by this flag.
  **Two more real bugs, caught by testing right after `--bookorbit-mode` was added, both fixed via code review:** (1) re-tagging a file with the flag *off* after a previous tag had it *on* left the old `.opf` on disk untouched, still carrying the previous match's data — the same "re-tagging must clear stale data" failure mode as the series bug above, just for a whole sidecar file instead of an XMP property this time. Fixed: `write_metadata()` now deletes any existing `.opf` whenever a write completes with `bookorbit_mode=False`. (2) `renamer.py`'s rename of a file's `.pdf`/`.opf`/`.metadata.json`/`.bak` group had no error handling around the actual `Path.rename()` calls — an `OSError` partway through a group (permission denied, a file locked by another app) propagated uncaught and crashed the whole batch instead of being reported as one failure among many, and could leave that file's companions split across old and new names. Fixed with a best-effort rollback of whatever in the group had already succeeded before reporting the failure; verified by forcing a failure on the second rename in a group and confirming the first one gets reverted.
  **A fourth real bug, found in a later full-codebase pass: `renamer.py`'s `_read_sidecar_metadata()` only guarded against a `.metadata.json` that fails to *parse* as JSON, not one that parses fine but has an unexpected shape** — e.g. a hand-edited sidecar with `series` simplified to a plain string instead of `{name, number}`, a very plausible mistake for someone editing the file by hand. That crashed with `AttributeError: 'str' object has no attribute 'get'`, taking down the *entire* `rename --root` batch over one malformed file — the same class of failure the mid-group rollback fix above exists to prevent, just one step earlier in the pipeline. Fixed to tolerate any non-matching shape (wrong top-level type, missing `metadata` key, `title`/`series` present but not the expected type) by treating it the same as "no data found," recovering whatever part is still valid rather than failing the whole file. Verified with reproductions for each shape variant, including confirming a valid `title` next to a malformed `series` still renames using the title, just without a series prefix.
  **A fifth, in the CLI itself:** adding single-file support to `rename` (it previously only accepted `--root`) copied `tag`'s `add_mutually_exclusive_group(required=True)` pattern verbatim — which silently broke `rename`'s own prior behavior of falling back to `config.yaml`'s `root:` when invoked with no arguments at all, something `scan`/`write-pdfs`/`all` still do today. `tag` never supported that bare-invocation fallback in the first place, so copying its stricter interface changed `rename`'s behavior as an unintended side effect, not a deliberate design choice. Fixed by dropping `required=True`; `cmd_rename`'s existing config-fallback logic already handled the rest correctly once argparse stopped blocking the path to it.

**`renamer.py`'s `_sanitize_component()` is a real path-traversal defense, not just filesystem-legality cleanup — worth stating explicitly since, unlike the API-key and CSV-injection findings above, this was designed in rather than found as a bug, and had never actually been written down.** `title`/`series` feed directly into a filesystem path (`_target_stem()` → the renamed filename), and both ultimately trace back to DriveThruRPG's *public* catalog — the same attacker-reachable source the CSV-injection finding is about, not just the user's own data. `_sanitize_component()` replaces every `/` (and NUL) with `-`, which — because `Path.with_name()` also independently rejects any component containing a separator — means a crafted title/series like `../../../../tmp/x` can never place a file outside the target directory; it just becomes a harmless literal string like `..-..-..-..-tmp-x`. Verified with an actual traversal attempt (not just read through): a malicious title/series fed through the full `tag --rename` combined flow (both a catalog-sourced candidate and hand-typed manual entry) stayed fully contained, confirmed nothing landed outside the target directory. Re-verify this if `_sanitize_component()`'s character set ever changes, or if `renamer.py`'s filename-building logic is ever duplicated elsewhere instead of reused (as `--rename` deliberately does via `_rename_one()`).
- Grimmory `.metadata.json`: schema confirmed from the actual Java DTOs in `github.com/grimmory-tools/grimmory` (`backend/src/main/java/org/booklore/model/dto/sidecar/*.java` — Grimmory is an independent fork of Booklore and kept its package names) and its `SidecarMetadataWriter.java` (confirms the `<stem>.metadata.json` naming convention). Unlike the OPF, isbn10/isbn13 are separate flat fields with no auto-detection on Grimmory's end, so `sidecar_writer._split_isbn()` buckets by digit count itself.
- Both are best-effort: a field with no data is just omitted from the output, matching how each app's own writer behaves. `pdf_writer.write_metadata()` calls the Grimmory writer unconditionally, and the BookOrbit `.opf` writer only when `bookorbit_mode=True` (see above), both after the embedded-PDF write succeeds, and catches `Exception` broadly (not just `OSError`) around each — any sidecar failure is logged, never raised, since losing a sidecar must not fail the whole write when the embedded metadata already succeeded. (The first version of this only caught `OSError`, which didn't actually match that guarantee; caught and fixed via code review.)

Don't reshuffle any of this mapping without checking the relevant module's docstring and the real app source first — it reflects explicit, verified choices, not defaults.

**Backups are one-time, not per-run.** `pdf_writer._backup()` only creates a `.bak` if one doesn't already exist, so the backup always represents the pre-tagging original even across repeated re-tagging runs — it must not be refreshed on every write.

**`review.py`'s CSV merge preserves user edits.** `merge_by_filename()` skips overwriting any row already marked `approved` when a fresh `scan` runs again — re-scanning must not clobber manual corrections.

**`review.csv` is a CSV/formula-injection target, not just a local file.** `matched_title`/`description`/`publisher`/`tags` are sourced from DriveThruRPG's *public* catalog — anyone can list a product there, so this is attacker-reachable content, not just the user's own data — and the documented `scan`/`write-pdfs` workflow has the user open `review.csv` by hand in a spreadsheet app. A crafted catalog listing title starting with `=`/`+`/`-`/`@` would be read as a formula by Excel/LibreOffice/Numbers. Fixed with the standard leading-apostrophe defang on write (`_defang_formula`) and a matching strip on read (`_refang_formula`), so the safety prefix never leaks into what actually gets written into a PDF. Found via a security audit ahead of making this repo public, not by request.
**That fix introduced its own regression, caught in a later full-codebase pass.** `csv.DictReader` fills a short/hand-edited row's missing trailing columns with `None` (its `restval` default) — and `review.csv` is explicitly meant to be hand-edited, so this is an easy state to reach. `_refang_formula()` called `.startswith()` unconditionally and crashed on that `None`, which `save_review()` could then also re-crash on if such a row got merged and written back out (`merge_by_filename()` → `save_review()`, e.g. during `scan --apply-review`). Fixed by making both `_defang_formula`/`_refang_formula` pass non-str values through unchanged rather than assuming every CSV cell is always a string.

**The GUI's confirm/series dialogs had the same "DriveThruRPG's public catalog is attacker-reachable" gap, in a different shape — found via a full security audit of the codebase, not reported.** `QLabel` defaults to `Qt::AutoText`, which auto-detects and renders anything that looks like markup as real rich text/HTML — and three labels in `gui_tag_flow.py` interpolated `meta.title`/`meta.authors_str()` (both straight from a catalog match) into a bare `QLabel(f"...")` with no explicit text format set: `ConfirmDialog`'s header and authors line, and `SeriesDialog`'s "Series for {book_title}:" prompt. A crafted catalog listing title containing `<b>`/`<a href>`/etc. would render as formatted text (or, in principle, other constructs Qt's rich-text subset supports) instead of literal text — on the one screen whose entire purpose is showing the user exactly what's about to be written, undermining that guarantee. Confirmed empirically, not just reasoned through: built a `ConfirmDialog` with a title of `"Evil Book <b>BOLD INJECTED</b>"`, rendered it, and the header showed literal bold text before the fix (the `QLineEdit` field below it was never affected — `QLineEdit` has no rich-text mode at all, so free-text fields were always safe; only bare `QLabel`s were the gap). Also confirmed `QListWidgetItem` (used for the candidate list) has no `textFormat` concept whatsoever and always renders literally, so that surface was never at risk despite showing the same catalog data. Fixed with `_plain_label()`, a `QLabel` wrapper that forces `Qt.TextFormat.PlainText`, used at all three sites; re-verified with the same crafted-title screenshot afterward showing literal `<b>BOLD INJECTED</b>` text, not bold.

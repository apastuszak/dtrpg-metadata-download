# HISTORY.md

Verification stories and bug post-mortems behind the non-obvious decisions in [CLAUDE.md](../CLAUDE.md). CLAUDE.md states the current rule; this file explains how each one was learned — read it when you want the "why," or before touching code in an area that's bitten this project before. Sections here mirror CLAUDE.md's own headings.

## Manual overrides loader

`load_manual_overrides()` used to crash outright on a plausible hand-edit mistake. It read each field with `meta.get(key, default)`, but that default only applies when the *key is missing* — an entry with a key present but blank (e.g. `source:` with nothing after it) parses to an explicit YAML `null`, which `.get()` happily returns as-is instead of falling back. Most fields just ended up silently wrong (`None` instead of `""`), but `source` went through `Source(meta.get("source", Source.MANUAL.value))` and crashed with `ValueError: None is not a valid Source` — taking down `tag`/`scan` entirely until the file was fixed, since this loader runs unconditionally at the start of both. The mistake is a plausible one specifically *because* most other fields in the documented template (`description: ""`, `product_url: ""`, etc.) genuinely are meant to be left blank, so a user has no obvious reason to treat `source:` differently. Fixed by switching every field to `meta.get(key) or default`, which treats an explicit `null` the same as a missing key.

A later full-codebase pass found two more gaps in the same loader: a bare `some_file.pdf:` line with nothing indented under it parses to `meta = None`, not an empty dict, and `.get()` on that crashed with `AttributeError` — fixed by skipping the entry with a warning instead of failing the whole file. And an invalid `source:` value (not one of `Source`'s enum values) raised `ValueError` uncaught — fixed by catching it and falling back to `MANUAL` with a warning, the same "recover what's valid, don't fail the whole file" convention as the rest of this fix.

## Testing

**`tests/test_tag_tui.py` already caught two real bugs during development, not just theoretical ones:** (1) `ManualEntryScreen`'s Submit button falls below the visible screen area on a standard-size terminal once the form has enough fields (Title through Product URL plus the Description text area) — `pilot.click("#submit")` failed with `OutOfBounds`, a real usability problem a click-only design would have hit for real users too, not just the test. Fixed by adding a `ctrl+s` keybinding that submits regardless of scroll position. (2) The first draft of `TagApp._manual_entry()` wrote directly after `ManualEntryScreen` submitted, skipping the "About to write: {title}" / confirm step every other path (candidate-pick, manual override) goes through — a real behavioral regression from the old `_manual_entry_flow()`, which always double-confirms even after manual entry. Caught because the test asserted on a `ConfirmScreen` widget id that turned out not to be on screen; fixed by routing manual entry through the shared `ConfirmScreen` too.

**`tests/test_gui_app.py`** drives `TagFlowController` directly with a scripted fake `notify` callback for the controller-only tests (no real widgets, no display needed, and no Qt import at all — `TagFlowController` is framework-agnostic); a handful of tests build the real highest-value dialogs and exercise the Review tab's table directly, both needing the one shared `QApplication` instance (Qt permits exactly one per process). One test (`test_tag_worker_signal_round_trip`) drives a *real* `QThread` end-to-end through the signal-based `_ask()` path — the single highest-novelty piece of the Tk→Qt migration, so it gets direct coverage beyond the fake-`notify` group. Another (`test_review_tab_no_save_during_population`) guards a real Qt-specific gotcha with no Tkinter analog: `QTableWidget.itemChanged` fires during programmatic bulk population just as it does for a real user edit, so `ReviewTab._populate_table()` must `blockSignals(True)` around it or every reload fires spurious commits.

**This test suite replaced an earlier Tkinter-based one, ported alongside the GUI rewrite (see "GUI: Tkinter → PyQt6 migration" below for why).** The old suite's highest-value caught bug — `ttk.Treeview.identify_column()` disagreeing with `.bbox()` about column boundaries, misrouting clicks to the wrong column — has no Qt equivalent: `QStyledItemDelegate` editor placement is entirely Qt-internal, so there's no manual hit-testing left to get wrong, and the ported Review-tab test is now a plain persistence smoke test rather than a hit-testing regression guard. A separate Tcl/Tk-specific `after()`-timer-during-`wait_window()` quirk that constrained how the old suite scheduled auto-interaction likewise has no Qt equivalent and wasn't carried forward.

**The candidate screen's "Pick" button/action never used the URL field, in both the TUI and the GUI — reported by the user, not caught by any test, since every existing test either picked a candidate or used the URL field, never both at once.** Pasting a URL and clicking Pick (a very natural thing to try) silently ignored the pasted text and used whatever was highlighted in the candidate list instead. Fixed by adding a dedicated **Use URL** button/action in both UIs, wired to the exact same submit logic Enter already used (`CandidateScreen._submit_url()` in `tag_tui.py`; `CandidateDialog._submit_url()` in `gui_tag_flow.py`) — Pick and Use URL are now unambiguously separate actions in both places, guarded by `tests/test_gui_app.py`'s `test_show_candidate_dialog_use_url_button`. Adding the TUI's button surfaced a second real bug: putting it in a `Horizontal()` alongside the full-width URL `Input` pushed it to `x=74` in an 80-column terminal (`Input` claims available width greedily) — clipped past the edge and unclickable, the same class of bug as `ManualEntryScreen`'s previously-documented off-screen Submit button, just horizontal instead of vertical. Fixed by moving Use URL into the row of standalone buttons below the `Input` instead, where it and Manual entry/Skip/Quit all fit comfortably (confirmed by checking each button's actual computed `Region` in a real `run_test()` session, not just by eyeballing the CSS).

## GUI: Tkinter → PyQt6 migration

**This project's GUI was originally built in Tkinter, then fully rewritten in PyQt6.** The trigger was an unresolved widget-rendering bug: a custom-bordered, scrollable Description field misaligned and never showed a focus ring on one real machine, despite the implementation being verified correct by every means short of running it there (property inspection, direct pixel-geometry measurement, a simulated real click) and despite a confirmed full process kill and relaunch. That bug was the latest in a run of subtle Tk/Tcl platform-rendering quirks this project kept hitting — Tk delegates widget painting to native OS APIs, which is exactly where each of these discrepancies traced back to. Qt paints its own widgets, so switching removes this whole class of bug by construction rather than working around one more instance of it. Two Tk-specific bugs the *old* GUI's test suite caught survive as historical record here since they were real bugs, just not toolkit-specific in their lesson: a `ttk.Treeview.identify_column()`/`.bbox()` disagreement about column boundaries (see "Testing" above), and the `RenameTab` dry-run-default bug (below, which is an application-logic bug that survived the rewrite unrelated to Tk). The border/rendering saga itself, and the Tkinter-only architecture notes that went with it (a `queue.Queue`+`root.after()` polling loop, and a keybinding hazard around `Toplevel`-level letter mnemonics), have no Qt analog and aren't detailed further here.

Under Tkinter, `UiTaskRunner` used `queue.Queue()`+`root.after()` polling to get log lines from a background thread to the log widget; under Qt, a queued signal connection does this automatically (Qt marshals a signal emitted from a worker thread onto the thread its connected slot's receiver lives on) — a real simplification, not just a port, and eliminated the polling loop entirely.

### The Description-field styling saga

**Even under Qt, the Description field (`QPlainTextEdit`) had a black border with no blue focus ring while every `QLineEdit` field around it had a grey border that turned blue on focus — the exact same visible symptom as the Tkinter bug that triggered the migration, for the exact same underlying reason.** `QLineEdit` gets a native-looking grey border (blue on focus) for free from Qt's macOS style, since qmacstyle draws it the way a real `NSTextField` would; `QPlainTextEdit`/`QTextEdit` don't get that same native treatment — their frame is just a generic `QFrame` panel with no focus-color change, since Qt has no equivalent native-control mapping for a multi-line text view. This took four real, independently-verified fixes to actually resolve — each one initially looked complete by reasoning about what Qt "should" do, and each was wrong until checked against an actual screenshot (`QWidget.grab()`, saved to a file and read back), which is why this is recorded in this much detail: **reasoning about Qt's stylesheet/focus system is not a substitute for looking at a real rendered pixmap.** All four fixes now live in one place, `_StyledTextEdit(QPlainTextEdit)` in `gui_app.py`, used everywhere a multi-line field is needed (`_make_log_widget()`, the Review tab's `_DescriptionEdit`, and both Tag-flow dialogs' description fields in `gui_tag_flow.py`) instead of a bare `QPlainTextEdit`:

1. **No border/focus styling at all initially** — fixed by adding a QSS rule (`_TEXT_EDIT_STYLE`): `QPlainTextEdit { border: 1px solid ...; } QPlainTextEdit:focus { border: 1px solid ...; }`. Unlike Tkinter (no declarative focus-state styling at all, requiring manual `FocusIn`/`FocusOut` bindings and a forced repaint), Qt's QSS supports `:focus` natively — in principle, one rule should have been enough.
2. **Applying that stylesheet via `QApplication.setStyleSheet()` (app-wide) fixed the Description field but silently killed the native blue focus ring on every `QLineEdit` in the app too** — caught from a real screenshot showing every field's focus ring gone, not just the untargeted ones. Setting *any* stylesheet on the `QApplication`, even one whose only selector is `QPlainTextEdit`, makes Qt route *all* widget painting through its `QStyleSheetStyle` proxy instead of the native macOS style, which suppresses native chrome (the focus glow) even for widgets the stylesheet doesn't target. Fixed by applying the stylesheet per-widget instead (in `_StyledTextEdit.__init__`) — a stylesheet set directly on one widget only affects that widget and its children, leaving sibling `QLineEdit`s on native rendering untouched.
3. **Still incomplete: rounded grey corners, but the four straight edges were still black** (a second real screenshot). `QPlainTextEdit` is a `QAbstractScrollArea`, which paints its own native `QFrame` panel independently of the QSS `border` property — the QSS border was being drawn, but the native sunken-panel frame was still painted too, visible wherever the square native frame didn't coincide with the QSS's rounded corners. Fixed by also calling `setFrameShape(QFrame.Shape.NoFrame)` before applying the stylesheet, removing the native frame layer entirely.
4. **Still not fixed after both of the above — "exactly the same."** This time verified with pixel-level precision rather than eyeballing: cropped a real screenshot and sampled the actual rendered border color of a genuine `QLineEdit` (`(235, 235, 235)` / `#ebebeb`) versus the guessed `_TEXT_BORDER_COLOR` that had been in use since the Tkinter version (`#a3a3a3` / `(163, 163, 163)`) — nearly 3x darker, which reads as "black" sitting next to a real `#ebebeb` border. Fixed by matching the measured value exactly instead of eyeballing a "plausible-looking grey."
5. **Separately, the `:focus` border still never rendered on a real focus change even with fixes 1-4 in place, despite `hasFocus()` correctly reporting `True`.** `QAbstractScrollArea` delivers keyboard focus through its internal `viewport()` child widget, not the outer widget the stylesheet targets, so the outer `QPlainTextEdit` never received its own `focusInEvent()`-triggered repaint the way a plain widget like `QLineEdit` would (confirmed by manually forcing `style().unpolish()`/`.polish()`/`.update()` after `setFocus()` and watching the blue border finally appear in an otherwise-identical screenshot). Fixed by overriding `focusInEvent`/`focusOutEvent` on `_StyledTextEdit` to do exactly that automatically on every focus change.
6. **Once colors/borders finally matched, the *focused* border still looked visibly thinner than native's, with corners that looked cut off rather than rounded — a real, if purely cosmetic, difference confirmed by comparing zoomed-in crops of both.** First tried nudging `_TEXT_EDIT_STYLE`'s focus state from `1px solid` to `2px solid` with a slightly bigger border-radius — a small improvement, but the user correctly called this "exactly the same" in substance: a flat QSS border, at any width, is still a crisp uniform line, and the real native ring (confirmed by pixel-sampling a real focused `QLineEdit`) is a soft ~3px pale band *outside* the control's own thin border, not a thicker/bluer version of that border. Asked the user how far to chase this (a solid border is "good enough" vs. a true custom-painted glow); they chose the glow.
7. **First glow attempt (`QGraphicsDropShadowEffect`, Qt's stock box-shadow-equivalent) was compared directly against a real screenshot, side by side, and was visibly wrong in its own way: darker and thinner near the edge, fading out fast, reading as a "shadow" rather than the native ring's fairly uniform pale band.** A Gaussian blur's density is inherently highest right at the source edge and falls off with distance — no combination of blur radius/opacity produces the flatter, more even-width band the real ring has. Replaced with `_FocusRingEffect`, a custom `QGraphicsEffect` subclass whose `draw()` paints an actual rounded-rectangle ring with `QPainter` (a fixed-width translucent stroke offset outward from the widget's own bounds) instead of approximating the shape through a blur algorithm — `boundingRectFor()` is what lets Qt reserve room to paint outside the widget's normal geometry, which a plain `paintEvent` override can't do.
8. **That first custom-ring version was itself wrong in two more ways, both reported directly from real screenshots (not caught by any self-review beforehand): a visible white gap between the ring and the field's actual border that native doesn't have, and corners distinctly rounder than native's own.** `RING_MARGIN` (the offset between the widget's own border and the ring) had been set to `2.0` on the assumption of a small breathing gap; a real screenshot showed native's ring sits flush against the control with no gap at all. `RING_RADIUS` had been set to `8.0`, visibly rounder next to a real native field's much more rectangular, barely-rounded corners. Fixed by setting `RING_MARGIN = 0.0` (flush) and `RING_RADIUS = 6.0` (closer to the ~5px native radius measured earlier), re-verified with a fresh side-by-side screenshot crop before calling it done.

### RenameTab dry-run bug

**`RenameTab`'s "Dry run (preview only)" checkbox defaulted to checked — a real bug, reported by the user as "I checked off rename and it did not rename the file" the first time they used it (an application-logic bug, not toolkit-specific — it survived the Tk→Qt rewrite as a fact to preserve, not fix again).** The CLI's own `--dry-run` flag is `action="store_true"` (off unless passed — `rename` really renames by default), but the GUI checkbox inverted that: clicking "Run Rename" without noticing and unchecking the box first silently only logged "Would rename: ..." and touched nothing, the opposite of what running the tab's primary button should do by default. Fixed by defaulting the checkbox to unchecked, matching the CLI. Verified against the real widget (not just the underlying function): filled in a path, left the checkbox untouched, clicked Run — file and sidecar actually renamed on disk. The Tag tab's own "Rename after write (--rename)" checkbox was never affected by this — it defaults to unchecked, matching `--rename`'s own `action="store_true"`, and correctly renames when checked.

## DriveThruRPG API reverse-engineering notes

`dtrpg_client.py`'s docstring records what's actually confirmed vs. inherited from third-party reverse-engineering — the API is undocumented, so treat field-path assumptions as provisional:

- `order_products` (purchased library, via `search_library`) and the `auth_key`/token auth flow were reverse-engineered from `glujan/drpg`'s source and are trusted.
- `products/{id}` (product detail — authors, publisher, description, tags) was *initially* modeled on `quickwick/drivethrurpg-calibre-plugin`, which assumes a JSON:API envelope (`{"data": {"attributes": ...}}`). That assumption was wrong against a real authenticated account — the live response is a **flat** object. `_parse_product_detail` is now written against the confirmed flat shape (verified from an actual `data/debug/` dump), not the plugin's code. If matching breaks again with a `KeyError` during product-detail parsing, check `data/debug/` for the raw dump before changing the parser blind.
- Catalog/product-detail endpoints were later confirmed to work with **no authentication at all** (a live, unauthenticated `search_catalog()` call returned correct results) — genuinely public by design, not an oversight; don't add an auth requirement there without re-confirming against a live response first.

**`auth_key` requires the application key as a URL query param (`?applicationKey=...`), which means `resp.url` for that call literally contains the key — a real leak surface, not just a theoretical one.** Two paths let it out: a failed JSON parse or missing `token` field used to dump the raw `resp.url` (key included) to a plaintext file in `data/debug/`, and any non-401 HTTP error let `requests.HTTPError`'s default message (which embeds the URL) propagate uncaught to the terminal/traceback — exactly what someone would paste into a bug report while asking for help. Fixed in `_authenticate()`/`_dump_debug()`: the debug-dump path now redacts the key wherever it appears in a URL (not just at this one call site, so any future endpoint that also leaks a secret into its URL is covered), and the `raise_for_status()` failure re-raises a sanitized `DtrpgApiError` with `from None` specifically so the key-bearing original exception is never chained into anything that gets printed. Found via a security audit ahead of making this repo public, not by request.

**A library entry's `productId` can go stale.** DriveThruRPG can re-list a purchased title under a new product ID after purchase (confirmed against a real purchase: "Delta Green: Handler's Guide" 403'd — `403.02`, "You cannot access this content right now" — on the ID from the user's `order_products` entry, while the current listing at a different ID fetched cleanly). `DtrpgClient.enrich()` handles this itself: on a failed direct fetch, `_enrich_fallback_by_title()` retries via `search_catalog(meta.title)` and, if found, also overwrites `meta.product_id` with the corrected one — necessary so the *right* ID ends up in the file's `dc:identifier`, not the dead one.

**That fallback originally accepted the first search result unconditionally, even with no title match at all** — a real bug found in a later full-codebase review: `candidates[0]` could be a completely unrelated product, risking merging a different product's description/ISBN into a purchased library entry and overwriting its `product_id` with the wrong listing's. Fixed to require a real fuzzy title match (rapidfuzz `token_sort_ratio` ≥ 70, matcher.py's own "review floor" threshold) before trusting a fallback result — verified empirically that matcher.py's *higher* `high_confidence_threshold` (90) was too strict for the real pattern this fallback exists for (a "(2nd Printing)"-style re-listing suffix scored ~79), while a genuinely unrelated title scored far lower (~36), so 70 was chosen as a bar that's real but doesn't reject the actual case.

## Image conversion (`image_converter.py`)

Ported from a separate personal project (`mac-pdf-rgb-fix`) that fixes CMYK/JPEG2000 images in PDFs for Apple's PDF renderer — ported, not merely called out to, since the two projects don't share a runtime. All of the source project's hard-won constraints were ported verbatim, not re-derived: CMYK images without an embedded profile get re-tagged with a real CMYK ICC profile before conversion (macOS's `Generic CMYK Profile.icc`; falls back cleanly elsewhere), output RGB images get an explicit sRGB ICC profile rather than bare `/DeviceRGB` (embedded both at the PDF colorspace level and inside the JPEG stream itself, since some decoders trust the JPEG's own profile over the PDF wrapper's), `/Mask` vs `/SMask` is preserved by checking the original object's key rather than assuming, shared image XObjects are processed once by xref not once per page, and `deflate_images` is never enabled on save (would silently undo the JPEG encoding).

**Verified concretely, not just reasoned through, that running this before pikepdf's metadata write is safe:** built a real PDF with an embedded CMYK JPEG, ran it through `write_metadata(..., convert_images=True)` with a series/index set, and confirmed with real `ebook-meta` (not pikepdf reading its own write) that `Series: Sword Worlds #2` still comes through correctly afterward — the exact structure this ordering exists to protect. Also verified: a JPEG2000 image's pixel values survive the JPX→RGB→JPEG round-trip exactly (a solid test color in, the identical value out), and a converted page still renders via `page.get_pixmap()` rather than coming back blank/corrupted.

**Image conversion is a heavier, riskier operation than metadata writing, so no dedicated committed test was added for it** — this project's convention is ad hoc verification scripts for pikepdf/PDF-writing logic generally (`pdf_writer.py` itself has none either, despite its own fragile Calibre-series history), with committed tests reserved specifically for UI screen/message-wiring risk (`tests/test_tag_tui.py`, `tests/test_gui_app.py`). The verification described above (a constructed CMYK+JPX PDF, real `ebook-meta` check, real page render) is the ad hoc equivalent for this module; re-run something like it if `image_converter.py`'s core loop ever changes.

## Sibling-script integrations (hyperlinking / grayscale / background-layer)

`rpg_hyperlink.py` used to be `gurps_hyperlink.py` (`hyperlink_gurps_pdf()`) before the Mongoose script was added — confirmed the two sibling scripts share an identical function signature and return shape before generalizing, rather than assuming.

**Verified concretely, not assumed, that running the hyperlink steps before pikepdf's metadata write is safe:** built a synthetic PDF, added a real link annotation via PyMuPDF's `insert_link()`+`saveIncr()` (the exact mechanism both sibling scripts use), then ran it through the same `pikepdf.open(..., allow_overwriting_input=True)` → `pdf.save(path)` sequence `write_metadata()` uses for its own metadata write, and confirmed the link annotation survives intact on the other side (`fitz.open(...).load_page(0).get_links()` — present, correct target page, unchanged).

**Verified directly, not assumed, that running grayscale conversion *before* the hyperlink steps is safe:** a link annotation added via PyMuPDF's `insert_link()`+`saveIncr()` survives Ghostscript's grayscale pass intact (confirmed by reading the link back with `fitz.get_links()`) — the sibling script's own `run_ghostscript()` already passes `-dPreserveAnnots=true`/`-c "/PreserveAnnotTypes [/Link] def"` for exactly this reason, but that claim was checked against a real link rather than trusted from the flag names alone. Also verified end-to-end that a Ghostscript-produced grayscale PDF survives a subsequent pikepdf metadata write (title/publisher both correct afterward).

**Verified directly, not just reasoned through, that background-layer tagging is safe to run first among the optional pre-write steps:** built a synthetic PDF with a `/Bg` image XObject wrapped in `q...Q` (the sibling script's `find_removal_span()` requires an enclosing bracket to identify a removable span — a real script constraint, confirmed when a first test PDF without the wrapping reported "skipped 1 pages" instead of actually removing anything), ran both tag mode and `--remove` mode through the wrapper, and confirmed with real `ebook-meta` that a subsequent pikepdf metadata write still comes through correctly afterward (`/OCProperties` present, `/OC` set on the Bg XObject in tag mode; the image gone entirely in remove mode).

**`Preferences` grew the four sibling-script paths (`gurps_hyperlink_script`/`mongoose_hyperlink_script`/`grayscale_script`/`background_layer_script`) instead of only being editable by hand in `config.yaml`'s placeholder keys.** `resolve_path(preference_value, config_value, default)` in `preferences.py` is the shared resolver — **deliberately the opposite precedence from `resolve_api_key()`**: the saved preference wins over `config.yaml`, not the other way around. This isn't an inconsistency, it's a different situation: `DTRPG_API_KEY` predates the Preferences feature by a long time, so protecting existing users of the environment variable from a silent behavior change mattered; these keys were only ever added to `config.yaml` as a stopgap in the same work that built the features using them, so there's no pre-existing workflow a saved preference could surprise. Verified directly: saving a script path via `PreferencesTab._save()`, reloading a fresh tab instance, and calling `resolve_script_paths()` with a *different* value also present in `config.yaml` all confirm the saved preference is what actually gets used.

**Manual overrides originally had no way to carry a `product_id` at all** — a real gap found in a later full-codebase review: an overridden book's `dc:identifier` was always empty, even when the override entry linked straight to the real DriveThruRPG listing via `product_url`. Fixed by deriving `product_id` from `product_url` via `extract_product_id()` (reused, not reimplemented) when no explicit `product_id:` key is given; verified end-to-end that a manual override's `product_url` now produces a real `xmp:Identifier` in the written PDF.

## Embedded PDF metadata: the Calibre series bug

**`pdf_writer._set_calibre_series()` exists because of a real, previously-undiscovered bug**: an earlier version wrote `calibre:series`/`calibre:series_index` as plain scalar XMP properties via pikepdf's public dict API. That round-trips through pikepdf perfectly (readable via `pikepdf.open(...).open_metadata().get(...)`) and was believed correct for most of this project's history — but real Calibre's reader (`read_series` in `xmp.py`) never actually recognized it: `calibre:series` must wrap its value in a nested `rdf:value`, and the index is a *differently-namespaced* child (`calibreSI:series_index`, URI `http://calibre-ebook.com/xmp-namespace-series-index`) nested inside the series element, not a sibling `calibre:series_index` property. Caught by testing against `ebook-meta --to-opf` on a real, never-before-touched file — a plain scalar write silently produces no "Series" line; watch for this failure mode (looks-fine-in-pikepdf, invisible-in-the-real-app) if any other Calibre-specific field is added later.

**Because this targets Calibre's actual XMP convention rather than something invented for this project, any reader that implements Calibre-compatible XMP parsing picks it up too — confirmed for Kavita, not just Calibre itself.** `Kavita.Services/Helpers/PdfMetadataExtractor.cs` in Kavita's real open-source repo (`Kareadita/Kavita`) explicitly registers the same `calibre`/`calibreSI` XMP namespaces and reads `//calibre:series/rdf:value` and `//calibreSI:series_index` — the exact nested structure `_set_calibre_series()` writes — plus standard `dc:title`/`dc:creator`/`dc:publisher`/`dc:description`/`dc:subject`. This is wired into Kavita's real scan path (`ReadingItemService.ParseFile()` → `BookService.GetComicInfo()` → `PdfComicInfoExtractor` → this extractor, gated only by a normal per-library "enable metadata" setting), not a dead/unreachable path like the BookOrbit `.opf` precedence trap below. **One real, confirmed gap: ISBN.** Kavita's PDF extractor looks for `pdfx:isbn` or `prism:isbn`, neither of which this project writes — ISBN here lives inside Calibre's own qualified `xmp:Identifier` Bag instead, which Kavita's PDF path never reads.

**Re-tagging a file must clear stale series data, not just add new data** — a third real bug, caught by code review right after the previous two. `write_metadata()` edits a PDF's *existing* persisted XMP tree in place (unlike `sidecar_writer.py`, which fully regenerates its output each run and so has no staleness exposure at all). The series-writing block only ran `if row.series:` — meaning re-tagging a file to a match with *no* series left all four series-related properties (`calibre:series` and its nested index, plus both `bookorbit:` fields) silently in place from whatever the previous match had. Fixed: an explicit `else` branch clears all four when the current match has none, and `bookorbit:seriesIndex` is explicitly deleted (not just left unset) whenever the current match has a series but no numeric index. Verified against both real `ebook-meta` and BookOrbit's real XMP reader across a full write → retag-different-index → retag-no-series sequence, not just a single write.

**That `else` branch was itself missing the `except AttributeError` guard every other private-pikepdf-internals call site has** — a gap found in a later full-codebase review. A future pikepdf version changing these internals would have crashed the whole write specifically when a match has *no* series, instead of degrading the same way every other Calibre-specific write already does. Fixed by wrapping it the same way, with the same warn-and-continue behavior; verified by injecting an `AttributeError` and confirming the write still succeeds (with a warning logged) instead of failing.

**ISBN validity is checked before writing** (`sidecar_writer._split_isbn()`, imported into `pdf_writer.py` for this) — this check existed in the BookOrbit-only era (`_isbn_field()`) and was accidentally dropped in the revert to Calibre format; restored via code review, not by request.

## BookOrbit `.opf` precedence trap and related bugs

**The `.opf` sidecar's series data is real but unreachable by BookOrbit in practice, given how its scanner actually works — this was a real bug, caught only after a user reported BookOrbit not importing series despite everything testing correct in isolation.** BookOrbit's default `metadataPrecedence` for PDFs is `['embedded', 'opfFile']` (confirmed from `scanner.constants`/`library.constants.ts`), and `extractFirstAvailableMetadataSource()` in `scanner.service.ts` stops at the *first* source that extracts *anything* — it's a whole-source fallback, not a per-field merge:

```ts
for (const source of sources) {
  const extracted = await this.extractMetadataSource(...);
  if (extracted) return;   // never reaches opfFile if embedded returned anything
}
```

Since a Calibre-tagged PDF always has *some* embedded metadata, `embedded` always "wins" and `opfFile` is never even opened — regardless of what's actually in it. This is why `bookorbit:seriesName`/`seriesIndex` are also written directly into the embedded PDF; don't assume the `.opf` is actually being read for series, or trust "the sidecar parses correctly in isolation" as proof a *scanned* BookOrbit library will show the data — verify end-to-end against the precedence logic too. This is also why the `.opf` is no longer written at all by default, only under `--bookorbit-mode`.

**Two more real bugs, caught by testing right after `--bookorbit-mode` was added, both fixed via code review:** (1) re-tagging a file with the flag *off* after a previous tag had it *on* left the old `.opf` on disk untouched, still carrying the previous match's data — the same "re-tagging must clear stale data" failure mode as the series bug above, just for a whole sidecar file instead of an XMP property this time. Fixed: `write_metadata()` now deletes any existing `.opf` whenever a write completes with `bookorbit_mode=False`. (2) `renamer.py`'s rename of a file's `.pdf`/`.opf`/`.metadata.json`/`.bak` group had no error handling around the actual `Path.rename()` calls — an `OSError` partway through a group propagated uncaught and crashed the whole batch instead of being reported as one failure among many. Fixed with a best-effort rollback of whatever in the group had already succeeded before reporting the failure; verified by forcing a failure on the second rename in a group and confirming the first one gets reverted.

**A fourth real bug, found in a later full-codebase pass: `renamer.py`'s `_read_sidecar_metadata()` only guarded against a `.metadata.json` that fails to *parse* as JSON, not one that parses fine but has an unexpected shape** — e.g. a hand-edited sidecar with `series` simplified to a plain string instead of `{name, number}`. That crashed with `AttributeError: 'str' object has no attribute 'get'`, taking down the *entire* `rename --root` batch over one malformed file. Fixed to tolerate any non-matching shape by treating it the same as "no data found," recovering whatever part is still valid rather than failing the whole file. Verified with reproductions for each shape variant, including confirming a valid `title` next to a malformed `series` still renames using the title, just without a series prefix.

**A fifth, in the CLI itself:** adding single-file support to `rename` (it previously only accepted `--root`) copied `tag`'s `add_mutually_exclusive_group(required=True)` pattern verbatim — which silently broke `rename`'s own prior behavior of falling back to `config.yaml`'s `root:` when invoked with no arguments at all. Fixed by dropping `required=True`.

## `renamer.py`'s path-traversal defense

`_sanitize_component()` is a real path-traversal defense, not just filesystem-legality cleanup — worth stating explicitly since, unlike the API-key and CSV-injection findings elsewhere, this was designed in rather than found as a bug, and had never actually been written down. `title`/`series` feed directly into a filesystem path (`_target_stem()` → the renamed filename), and both ultimately trace back to DriveThruRPG's *public* catalog — the same attacker-reachable source the CSV-injection finding is about, not just the user's own data. Verified with an actual traversal attempt (not just read through): a malicious title/series fed through the full `tag --rename` combined flow (both a catalog-sourced candidate and hand-typed manual entry) stayed fully contained, confirmed nothing landed outside the target directory.

Re-verified after a later change widened the sanitized character set from just `/`+NUL to also include the Windows/SMB-reserved set (`\:*?"<>|`), protecting against a real failure mode if the library is ever accessed over SMB/exFAT/a Windows-formatted drive: re-ran the same traversal attempt (`../../../../tmp/x:evil` with a colon added specifically to exercise the new character set) and confirmed nothing escaped the target directory, and that the new characters get replaced correctly alongside the original two.

**That colon change read badly on its own, for the single most common case it actually affects — a real bug caught in review, not by any test.** `": "` is an extremely common shape in RPG titles (`"Delta Green: Handler's Guide"`), and the first version of this change ran it through the same generic character-to-hyphen substitution as every other unsafe character, producing `"Delta Green- Handler's Guide"` — a hyphen butted right up against the preceding word, with no space before it, reading as a typo rather than a deliberate separator. Fixed by special-casing a colon followed by whitespace (`_COLON_SUBTITLE_RE = re.compile(r"\s*:\s+")`) to `" - "` first, consuming any surrounding whitespace so `"Title : Subtitle"`/`"Title  :  Subtitle"` don't leave a double space behind either — before the general substitution runs on whatever's left. A colon with no trailing space (`"Title:Subtitle"`, or one at the very end of a string) still falls through to the general substitution unchanged. Re-verified the path-traversal defense held with this second change too, and that an already-correctly-renamed file (under the old, pre-this-change naming) triggers exactly one corrective rename and then stays stable — it doesn't keep renaming itself on every subsequent run.

## `review.csv` as an injection target

**`review.csv` is a CSV/formula-injection target, not just a local file.** `matched_title`/`description`/`publisher`/`tags` are sourced from DriveThruRPG's *public* catalog — anyone can list a product there, so this is attacker-reachable content, not just the user's own data — and the documented `scan`/`write-pdfs` workflow has the user open `review.csv` by hand in a spreadsheet app. A crafted catalog listing title starting with `=`/`+`/`-`/`@` would be read as a formula by Excel/LibreOffice/Numbers. Fixed with the standard leading-apostrophe defang on write (`_defang_formula`) and a matching strip on read (`_refang_formula`), so the safety prefix never leaks into what actually gets written into a PDF. Found via a security audit ahead of making this repo public, not by request.

**That fix introduced its own regression, caught in a later full-codebase pass.** `csv.DictReader` fills a short/hand-edited row's missing trailing columns with `None` (its `restval` default) — and `review.csv` is explicitly meant to be hand-edited, so this is an easy state to reach. `_refang_formula()` called `.startswith()` unconditionally and crashed on that `None`, which `save_review()` could then also re-crash on if such a row got merged and written back out. Fixed by making both `_defang_formula`/`_refang_formula` pass non-str values through unchanged rather than assuming every CSV cell is always a string.

**A related gap, found in a later full-codebase review: `load_review()` converted a short row's `None` fields via `_refang_formula`, but the result (still `None`) was passed straight into `ReviewRow`'s typed-`str` fields.** Downstream code assuming every field is a real string (e.g. `row.tags.split(";")` in `pdf_writer.py`) crashed with `AttributeError` on such a row, partway through a `write-pdfs` batch. Fixed by coercing `None` to `""` in `load_review()` itself, matching `ReviewRow`'s own field defaults.

## GUI: QLabel rich-text injection

**The GUI's confirm/series dialogs had the same "DriveThruRPG's public catalog is attacker-reachable" gap as the CSV-injection finding, in a different shape — found via a full security audit of the codebase, not reported.** `QLabel` defaults to `Qt::AutoText`, which auto-detects and renders anything that looks like markup as real rich text/HTML — and three labels in `gui_tag_flow.py` interpolated `meta.title`/`meta.authors_str()` (both straight from a catalog match) into a bare `QLabel(f"...")` with no explicit text format set: `ConfirmDialog`'s header and authors line, and `SeriesDialog`'s "Series for {book_title}:" prompt. A crafted catalog listing title containing `<b>`/`<a href>`/etc. would render as formatted text instead of literal text — on the one screen whose entire purpose is showing the user exactly what's about to be written. Confirmed empirically: built a `ConfirmDialog` with a title of `"Evil Book <b>BOLD INJECTED</b>"`, rendered it, and the header showed literal bold text before the fix (the `QLineEdit` field below it was never affected — `QLineEdit` has no rich-text mode at all, so free-text fields were always safe; only bare `QLabel`s were the gap). Also confirmed `QListWidgetItem` (used for the candidate list) has no `textFormat` concept whatsoever and always renders literally, so that surface was never at risk despite showing the same catalog data. Fixed with `_plain_label()`, a `QLabel` wrapper that forces `Qt.TextFormat.PlainText`, used at all three sites; re-verified with the same crafted-title screenshot afterward showing literal `<b>BOLD INJECTED</b>` text, not bold.

## Robustness pass (full-codebase review)

A later full-codebase review turned up a batch of real, reproducible bugs, each verified with a targeted repro before fixing:

- **GUI Tag runs used to hard-crash the whole app on any exception.** A PyQt6 slot running on a `QThread` has no default exception handler — verified with a standalone repro that an uncaught exception there aborts the whole process (`SIGABRT`), not just the one background job. Fixed by wrapping `TagWorker.run()` in a try/except that logs instead, plus a `sys.excepthook` backstop in `run_gui()` (independently confirmed to prevent the abort).
- **Data paths (`data_dir`/`review_csv`/`manual_overrides`/`preferences`/sibling-script paths) resolved against the current working directory, not `config.yaml`'s own location.** Verified: running `tag` from another directory silently created a stray `data/` folder there and reported "No DriveThruRPG API key found" even with one saved in the real `data/preferences.yaml`. Fixed in `load_config()`; `root` is deliberately excluded since it behaves like a CLI argument, not an internal data file.
- **`write_approved()` used a row's filename as an `rglob()` glob pattern**, so a real filename containing glob-special characters (verified: `"Sword Worlds [OCR].pdf"` matched nothing, since `[OCR]` is a character class) was silently reported as "file not found under root." Fixed by building a plain `name -> Path` index once instead; also now warns once on a duplicate filename across subfolders rather than silently picking whichever `os.walk()` sees first.
- **Case-only renames (e.g. `sword worlds.pdf` → `Sword Worlds.pdf` on APFS) failed as "target already exists"**, since the target path already exists as the very file being renamed on a case-insensitive filesystem. Fixed by checking `new.samefile(old)` before treating it as a real collision; verified the rename actually updates the on-disk casing.
- **`scan_pdfs()` picked up macOS `._*` AppleDouble sidecar files** (common on SMB/exFAT shares) as if they were real books. Fixed by skipping dotfiles. Sibling-script/image-conversion temp files also got a hidden `.dtrpg-tmp-` prefix for the same reason — a force-killed run must not leave a "book" behind for the next scan to pick up and try to match.
- **No HTTP request in `dtrpg_client.py` had a timeout, and `max_retries` was stored but never used.** A stalled connection could hang the whole run forever. Verified with a real request to a non-routable address that it now times out and retries with backoff instead of hanging.
- **`save_review()` and the client's JSON caches wrote directly to their target path, not atomically.** A crash/kill partway through could truncate `review.csv`, silently losing every approved/hand-edited row it held. Fixed with the same temp-file-then-`os.replace()` pattern used elsewhere in this project; verified a simulated mid-write crash leaves the original file byte-for-byte intact with no orphaned temp file.
- **`write_approved()` only caught `(pikepdf.PdfError, OSError)` around the whole per-file write, so any other unexpected exception aborted every remaining file in the batch.** Fixed by catching any exception per file and recording it as one failed `WriteResult` instead; verified with an injected `ValueError` on the middle file of three that the other two still get processed.
- **The background-layer subprocess had no timeout**, so a genuinely hung child process (not one that just fails/exits) could block a run forever. Fixed with a 300-second timeout; verified with a real hung subprocess that it fails cleanly instead of blocking, with no orphaned temp file.
- **Editing a row in the GUI's Review tab (e.g. its series) without also flipping `status` to `approved` used to be silently discarded by the next `scan`.** `merge_by_filename()` only ever protected rows already marked `approved`. Fixed by adding `ReviewRow.edited`, set by the Review tab's real commit paths (inline table edits, the detail form, the description field) whenever a field actually changes; `merge_by_filename()` now preserves any edited row too. Verified end-to-end through the real Qt widget path (an actual `QTableWidgetItem.setText()`, not just calling `mark_edited()` on a plain object), and confirmed backward compatible — an old `review.csv` with no `edited` column loads exactly as before.

Every fix above was verified with a targeted reproduction, not just read through; `tests/test_gui_app.py` gained regression tests for the exception-handling, re-scan-preservation, and worker-crash fixes specifically, since those are the same class of UI-wiring risk this suite already exists to catch.

### Regressions found in a follow-up review of the pass above

A review of the robustness-pass fixes above turned up two real regressions those fixes had themselves introduced — worth recording as a reminder that a fix touching a widely-called function needs checking against every caller's own assumptions, not just the one call site being fixed:

- **The new retry-with-backoff raised `RetryError` once retries were exhausted on a persistent 429/5xx, instead of handing back the failed response.** Every existing caller in `dtrpg_client.py` was written against "get a `Response` back, then decide what to do" (`resp.status_code == 401`, `resp.ok`, `resp.raise_for_status()`) — `_fetch_product_detail()` in particular is called directly by `get_product()`/`enrich()` with no try/except of its own, since its whole contract was "return `None` on failure, never raise." Verified against a real server that always returns 503: `get_product()` used to raise `RetryError` uncaught, which would abort an entire `scan`/`tag` run over one bad known-URL lookup instead of falling back to search the way `match_file()`'s own code already expected. Fixed with `raise_on_status=False` on the `Retry` policy (restores "hand back the failed response" for exhausted status-based retries — verified the 401 and exhausted-retry-500 paths in `_authenticate()` still raise `DtrpgApiError` correctly, since those still go through `resp.raise_for_status()`/an explicit status check, not urllib3's own exception), plus a try/except around `_fetch_product_detail()`'s own request for connection-level failures (a real non-routable-host timeout) that survive retrying and would otherwise still propagate.
- **The Review tab's detail-form fields and description box marked a row "edited" on every focus-out, whether or not the value actually changed.** `editingFinished`/`focus_lost` fire whenever focus leaves the widget, unlike `_on_item_changed` (the inline table-cell path), which only fires on a real Qt-detected change. Simply clicking into a field to read it, then tabbing away with no edit, permanently exempted that row from ever being refreshed by a later re-scan — for a field the user never actually touched. Verified through the real widget: focusing then leaving `publisher`/`description` with no change left `edited` blank; changing the text first still set it correctly. Fixed by comparing the new value against the current one before calling `mark_edited()`; guarded by `tests/test_gui_app.py`'s `test_review_tab_no_change_does_not_mark_edited` (confirmed this test actually catches the regression by temporarily reintroducing the unconditional `mark_edited()` call and re-running the suite).

A third, unrelated issue was also found and fixed in the same pass: `save_review()`/`_save_json()`'s new atomic write (`tempfile.mkstemp()` + `os.replace()`) silently tightened the target file's permissions to `0600` on every save, since `mkstemp()` always creates its file owner-only and `os.replace()` preserves that mode on POSIX — `review.csv` going from a normal `644` down to `600` would break anything else expecting to read it (a NAS share, another process). The first fix for this read the process umask at save-time via `os.umask(0)` then `os.umask(saved)` to compute a fallback mode for a brand-new file — itself a real bug, since that trick briefly sets the *process-wide* umask to `0`, and both save functions run on background `QThread`s in the GUI; a file created by an unrelated thread in that instant could come out world-writable. Fixed by reading the umask once at module import time instead (single-threaded, before any background thread exists), stored as a module-level constant and reused at save-time with no further `os.umask()` calls — this closes the race by construction (there's no longer any `os.umask()` call during a save for a competing thread to be affected by), not by luck of timing. Verified the existing-file-permission-preservation behavior is unchanged. A 200-iteration concurrent-saves stress test was also run and produced no world-writable files, but that's a weak check on its own for a race this narrow (a few-microsecond window the old code could easily have "passed" the same way most of the time) — it wasn't run against the pre-fix code for comparison, so treat it as a smoke test that found nothing, not as proof the old code was racy or that the fix closes it; the by-construction argument above is what actually establishes that.

## Watermark detection/removal (`watermark_removal.py`)

A fourth kind of sibling-script integration, but a genuinely different shape from the other three: wraps `remove_dtrpg_watermarks.py`, from a *different* sibling repo (`text-removal`, not `gurps_4e_revised_hyperlink`) that happens to also live on this machine. The sibling script's own `main()` has no separable non-interactive entry point at all -- every step (auto-detect vs. free-text search, which candidate to remove, confirm-before-removing) is an `input()` prompt baked directly into `main()`'s body -- but its detection/removal *logic* was already factored into real top-level functions (`collect_lines`/`detect`/`scan`/`strip_from_streams`), so `watermark_removal.py` loads those the usual way (`importlib.util.spec_from_file_location`) and reproduces `main()`'s post-confirmation removal sequence directly against them, rather than re-deriving it independently.

**Verified against a real synthetic watermarked PDF (5 pages, a repeating "www.drivethrurpg.com" line in the lower-left corner of every page), not just read through:** `detect_watermark()` correctly found the candidate (`page_count=5`, `total_pages=5`); `remove_watermark()` removed it via `strip_from_streams()` with zero fallback needed, and the real page content survived untouched; re-running `detect_watermark()` on the cleaned file found nothing. Separately forced the redaction-fallback branch (by patching `strip_from_streams()` to report everything as unremovable in-stream, simulating a shared/unowned content stream) and confirmed the watermark still comes out and real content still survives, exercising the one code path the happy-path test above doesn't reach. Also verified the same ordering guarantee every other pre-write step in this project is held to: a watermark-removed file survives a subsequent pikepdf metadata write correctly (title, series all come through).

**Interactive by design, unlike the other three sibling-script integrations, which are opt-in flags applied unconditionally once turned on.** The user's own request was specifically "check for a watermark and tell the user... ask if they'd like it removed" -- an automatic detect-then-confirm flow, not a flag. This ruled out reusing the `--background-layer`-style "boolean flag + GUI checkbox" pattern: the feature only makes sense where a human can actually answer a question, so it's wired into `tag` only (`TagApp._process_one()`/`TagFlowController._process_one()`, both TUI and GUI), never `write-pdfs`/`all`, which are non-interactive batch paths by design (the same reason candidate-pick/manual-entry/series-prompt are `tag`-only). Deliberately given no on/off flag on top of the script-path gate either -- `detect_watermark()` already returns `None` with zero user-visible effect when `watermark_script` isn't configured (this feature's real off switch), and once it *is* configured, the per-file Yes/No modal is the only gate a user should need; adding a second flag on top would just be one more setting to remember for a feature whose entire point is asking first. **Superseded by the vendoring change below**: there's no `watermark_script` setting anymore, so this paragraph's "off switch" is now just history -- the script is always present, and detection always runs unconditionally on every file `tag` processes, with no configuration step and no way to skip it.

**Runs before matching starts, not just before the metadata write** -- the one place this diverges from the "runs right before write_metadata()'s own pikepdf.open()" pattern the other three optional steps follow. Reasoned through, not just asserted: `detect_watermark()`/`remove_watermark()` both re-save the PDF via PyMuPDF, so the existing "every non-pikepdf step must run before pikepdf's write" rule already requires this to happen before write_metadata()'s final write regardless -- doing it before matching too, rather than merely before the write, closes a real (if narrow) window where a later optional step (image conversion, hyperlinking) could otherwise run against a still-watermarked file if the modal happened to land between matching and writing instead of before everything.

**Guarded by committed UI-wiring tests in both `tests/test_tag_tui.py` and `tests/test_gui_app.py`, matching this project's convention that new interactive TUI/GUI wiring gets a real test, not just an ad hoc script -- `detect_watermark()`/`remove_watermark()` themselves are mocked in every one of them (the same way `DtrpgClient` always is), so none of these tests need the real sibling script or its real machine-specific path present.** Verified each new test actually catches the regression it guards by temporarily reintroducing the bug (removing the `_maybe_remove_watermark()` call from `_process_one()` in both `tag_tui.py` and `gui_tag_flow.py`) and confirming the corresponding test fails, then restoring the fix and confirming it passes again -- not just that the test exists and currently passes.

## The sibling-script integrations were vendored, not just configured

**Every previous integration in this family (GURPS/Mongoose hyperlinking, grayscale conversion, background-layer tagging, and watermark removal) originally loaded its script from a configurable, machine-specific absolute path -- set via the saved Preferences file or `config.yaml`, resolved at runtime by `preferences.py`'s `resolve_path()`.** This was a deliberate choice at the time: these scripts were separate, independently-versioned projects living in sibling repos on the machine this project was built on, and hardcoding a real path from that machine into a committed file would have leaked a real person's home directory/username into a repo meant to go public (see the GURPS-hyperlink integration's own original history for exactly that mistake, caught and fixed). The configurable-path design was the fix for that -- `config.yaml` shipped generic `/path/to/...` placeholders, and the real value belonged in the gitignored, uncommitted Preferences file instead.

**That configurability turned out to be a real, hit-in-practice failure mode, not just a theoretical one: it's exactly what made the watermark-removal integration silently do nothing the first time it was used for real.** The feature was implemented, tested, and documented correctly -- but `watermark_script` was never actually set in either `config.yaml` or the real `data/preferences.yaml`, so `detect_watermark()` correctly (but silently) returned `None` on every file, with no error, no warning, nothing visibly wrong. The user reported "the script did not detect and offer to remove the watermark" on a real file; debugging confirmed the wrapper itself worked perfectly once pointed at the real script path (detected a real watermark across all 322 pages of a real book on the first try) -- the entire gap was that nothing had ever prompted the user to configure the path in the first place. This is the general risk any "off unless configured" design carries: the unconfigured state and the "working correctly, nothing to do here" state are visually and behaviorally identical, so there's no signal that anything needs attention.

**The fix chosen was to stop configuring these paths at all: copy all five scripts into this project's own directory as plain, committed files, and have each wrapper module resolve its own script's location as `Path(__file__).parent / "<script>.py"` -- a fixed, always-present path, not a setting.** This was a direct, explicit trade-off, decided with the user rather than assumed: the alternative (keep the Preferences/config.yaml path as an optional override on top of a vendored default) would have preserved some flexibility (pointing at a different copy, e.g. on another machine) at the cost of keeping the exact failure mode that had just caused a real bug. The user chose to remove the configuration surface entirely rather than keep it as a fallback.

This changed a genuinely large surface area, not just the five wrapper modules: `pdf_writer.py`'s `write_metadata()`/`write_approved()`, `tag_tui.py`'s `TagApp`, `gui_tag_flow.py`'s `TagFlowController`/`TagWorker`, and `dtrpg-metadata-download.py`'s `cmd_write_pdfs()`/`cmd_tag()` all previously threaded four or five `*_script` parameters through their signatures purely to plumb a configurable path down to the point of use -- every one of those parameters was removed, since there was no longer anything to plumb. `preferences.py`'s `Preferences` dataclass dropped all five script-path fields and the now-unused `resolve_path()` function; `gui_app.py`'s `resolve_script_paths()` (and its per-tab call sites) and `dtrpg-metadata-download.py`'s `_resolve_script_paths()` were deleted outright; the GUI's Preferences tab lost its five `QLineEdit`+Browse-button rows (and the `_path_row()`/`_browse_script()` helpers that built them) along with the TUI's five matching `Input` fields; `config.yaml` lost the five placeholder keys.

**Verified the vendored scripts actually work correctly from their new location, not just that the code compiles** -- re-ran a synthetic-PDF watermark-detection/removal check (a real synthetic watermarked PDF, detection, removal, redaction-fallback path) and the background-layer verification (a synthetic PDF with a `/Bg` XObject, tag mode) against the copied files with no `script_path` argument at all, confirming both `GURPS_HYPERLINK_SCRIPT`/`MONGOOSE_HYPERLINK_SCRIPT`/`GRAYSCALE_SCRIPT`/`BACKGROUND_LAYER_SCRIPT`/`WATERMARK_SCRIPT` resolve to real files inside this project's own directory, and that `write_metadata(..., background_layer=True)` still succeeds end-to-end through the full pipeline (metadata write included) with no script-path keyword argument anywhere in the call. This synthetic-PDF check was not the same test as the original feature-build verification and did not re-touch the real user file that had originally exposed the missing-configuration bug -- a follow-up review pass (see "Opus's post-vendoring review" below) did run the vendored path against that real file directly and confirmed it still works (322 pages, watermark detected in 5.1s), closing that gap.

An existing `data/preferences.yaml` with the old five script-path keys still loads without error or migration -- `load_preferences()` only ever read the fields it explicitly asks for, so the now-unused keys are silently ignored rather than causing a crash; saving preferences again through either UI naturally drops them from the file, since the new `Preferences` dataclass no longer has anywhere to put them.

## Opus's post-vendoring review: a real backup-ordering regression

**A second model, asked to independently review the vendoring work rather than just re-read it, found a real bug before it was committed: watermark removal skipped the project's one-time `.bak` backup.** `pdf_writer.backup()` (then still private, `_backup()`) was normally the very first thing to touch a file during a write, guaranteeing the `.bak` always captured the true pre-tagging original -- but watermark removal runs *before* `write_metadata()` is ever called (it's the first step in `_process_one()`, ahead of matching itself), and it saves the PDF in place via PyMuPDF. A file whose watermark was removed and then skipped (never reaching a full write) ended up modified on disk with no backup at all; a file that did proceed to a full write got a `.bak` that captured the *watermark-removed* copy, not the true original -- silently violating this project's own documented "backup is always the pre-tagging original" guarantee.

**Fixed by making `backup()` public and calling it explicitly, in both UIs, immediately before `remove_watermark()` runs** (`tag_tui.py`'s `TagApp._maybe_remove_watermark()`, `gui_tag_flow.py`'s `TagFlowController._maybe_remove_watermark()`) -- with an `OSError` guard that skips the removal entirely (leaving the watermark in place) rather than proceeding with no backup to fall back to if the backup itself fails.

**Verified with a real reproduction in both UIs before trusting the fix, not just by reasoning about it:** built a synthetic watermarked PDF, drove `TagApp`/`TagFlowController` through the real Yes/No modal and a subsequent skip, and confirmed directly against the resulting `.bak` and main file that the backup exists, matches the pre-removal bytes exactly, and the watermark is gone from the main file but still present in the backup.

**The first regression test written for this (`tests/test_gui_app.py`) didn't actually guard anything, and that was caught before it shipped, not after.** `_drive_controller()` runs `TagFlowController.run()` on a background `threading.Thread`; the test's mock `side_effect` used a bare `assert` to check the backup's state, but an `AssertionError` raised inside a function called from a background thread doesn't propagate to the main thread or the test runner -- the thread just dies silently (a traceback goes to stderr only), and `thread.join()` doesn't re-raise it. Confirmed empirically: deliberately reverted the `backup()` call in `gui_tag_flow.py` and reran the suite -- it still reported every test passing, including the one meant to catch exactly this. Fixed by having the mock record observations into a plain list instead of asserting inline, then asserting on the recorded list from the main thread after `_drive_controller()` returns (by which point its internal `thread.join()` has already completed) -- re-verified the same way, by reverting the fix again and confirming this corrected version of the test now correctly fails, then restoring the fix and confirming the full suite passes again. `tag_tui.py`'s own equivalent test never had this problem. `remove_watermark()` does run on a worker thread there too (`TagApp._call()` is `asyncio.to_thread()`), but `to_thread()` re-raises the thread's exception into the awaiting coroutine, so the failure reaches the Textual worker and fails the test. This was confirmed the same way, by reverting `tag_tui.py`'s fix: 16/17 passed, with this test the one failure. The `OSError` guard (backup fails, so removal is skipped) has no committed test; it was checked with a one-off script that patched `backup()` to raise in both UIs and confirmed `remove_watermark()` was never called.

**Separately, Opus flagged that watermark detection now runs unconditionally on every file `tag` processes (~5 seconds per book on a real 322-page PDF, confirmed measured), with no way to skip it** -- the old configurable `watermark_script` path was, incidentally, also the feature's only off switch; vendoring removed that along with the rest of the configuration surface. Put to the user directly rather than decided unilaterally: keep it as-is, no flag -- the per-book cost was judged small enough not to be worth a setting nobody would remember to use.

## Pre-write steps made processed books owner-only

**Found in a full-codebase review, confirmed with real files before fixing: `--background-layer`/`--remove-background`, `--convert-grayscale`, and `--hyperlink-gurps`/`--hyperlink-mongoose` each left a successfully processed book at `0600` (owner read/write only), whatever its permissions were before.** Every wrapper writes to a `tempfile.mkstemp()` file (always created `0600`) and then `os.replace()`s it over the book, which carries the temp file's mode along. Whether that mode survived depended on which library wrote the output: pikepdf's `save()` (the background-layer script, and the grayscale script's final metadata-restore pass) and `shutil.copyfile()` followed by PyMuPDF's `saveIncr()` (both hyperlink scripts) write *into* the existing temp file and keep its `0600`; PyMuPDF's full `save()` (watermark removal, `--convert-images`) recreates the file and happened to get a normal umask-derived mode. The same class of bug had already been fixed for `review.csv` and the DriveThruRPG cache files (`review.py`/`dtrpg_client.py`), but the fix hadn't reached the PDF-rewriting wrappers. It matters in practice because a reader app running as a different user (BookOrbit/Grimmory in Docker, or a library shared over the network) can't read an owner-only file.

**Fixed with `shutil.copymode(path, tmp)` right before every one of the five `os.replace()` swaps**, including the two that weren't currently affected, so correctness no longer depends on which library happens to do the writing. Verified by processing test PDFs through all five steps starting at both `0644` and `0664`: each ends at exactly its starting mode (the `0664` case shows the mode is copied from the original, not just defaulted from the umask). Books already processed with those flags before this fix are still `0600` and need a one-time `chmod`.

**Smaller fixes from the same review:**
- **No feedback during the watermark check.** The ~5-second scan per book showed a blank screen in the terminal UI and nothing in the GUI log, which looks like a hang. Both now show "Checking X for a watermark..." — a toast in the terminal UI and a log-widget line in the GUI, deliberately kept out of `history`/the run summary since it's progress, not an outcome.
- **Detection overstated its confidence.** It flags any lower-left line repeating on at least 90% of pages, which a publisher's own copyright footer can also do, and on a 1-4 page PDF almost any corner line qualifies. The vendored script's own `main()` warns about short documents; the wrapper had dropped that. Both UIs now word it as a *possible* watermark, warn that it could be a normal footer, and add the short-document warning below `WEAK_EVIDENCE_PAGE_COUNT` (5, matching the script). The wording lives in one shared function, `watermark_removal.describe_detection()`, so the two UIs can't drift. The terminal UI's labels now pass `markup=False`: the text comes from inside the PDF, and Textual would otherwise parse something like `[/]` in it as markup.
- **`--rename` left the hyperlink report behind.** `<stem>_link_report.csv` wasn't in `renamer._companion_pairs()`, so it stayed under the old name. Now it moves with the PDF like the other companions (verified with a PDF plus `.bak`, `.metadata.json` and `_link_report.csv`, all renamed together; `.opf` wasn't in that test but uses the same unchanged code path).
- **GUI log said "Stopped." then "Run complete."** after quitting mid-batch, and "Stopped." twice after closing the window. `TagFlowController.run()` now logs exactly one of the two.
- **Three GUI labels showed the filename in a rich-text-capable `QLabel`**; switched to `_plain_label()` like the other labels that show outside text.

**Two follow-ups from a second review of that fix:**
- **`copymode()` is best-effort.** As first written, a `shutil.copymode()` failure (some network filesystems refuse `chmod`, and this machine does have an SMB share from a NAS mounted) raised inside each wrapper's `try` and turned an otherwise-successful step into a failure, leaving the book unprocessed. Each call is now wrapped in `except OSError: pass`: keeping the original permissions is worth doing, but not worth failing the step over.
- **The terminal UI had the same "outside text parsed as formatting" gap the GUI fix closed, in more places.** Textual parses its own `[...]` markup in `Label`/`Static`, in `notify()` toasts, and in a plain-string `OptionList` prompt. Confirmed in the installed Textual 8.2.8: a real library filename, `Sword Worlds [OCR].pdf`, rendered as `Sword Worlds .pdf` (the unknown `[OCR]` tag silently swallowed), and any text containing `[/]` raised `MarkupError` and crashed the app. Affected: filenames in the candidate/manual-entry headers, catalog titles/authors on the confirm screen and series prompt, catalog titles in the candidate list itself, and every status toast ("Wrote metadata to …"). Fixed with `markup=False` on each of those widgets and on `notify()`, and by wrapping candidate-list prompts in Rich's `Text()` (confirmed to render literally, and available in every Textual version, unlike `textual.content.Content`). `notify(markup=...)` only exists from Textual 4.0 (checked 0.60, 0.86, 1.0, 2.0, 3.0: absent; 4.0 onward: present), so the declared `textual>=0.60` floor was raised to `textual>=4.0` in the PEP 723 header, both test scripts' headers, and `requirements.txt`. `uv` already resolves 8.x, so nothing changes in practice; the floor just no longer claims support for versions this code can't run on.
